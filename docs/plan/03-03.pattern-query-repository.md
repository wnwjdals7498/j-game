## 결정성 — 가장 중요한 제약

1단계 DoD가 "같은 (spec, repository 내용, seed) → 같은 Puzzle" 이다.
그러려면 `findByPattern` 이 **같은 인자에 같은 순서**를 돌려줘야 한다.

> `RANDOM()`은 결정성을 깨므로 **seed 기반 정렬**이 필요하면 후보를 넉넉히(limit×3) 가져와
> Dart에서 `Random(seed)`로 섞는다.

**결론: SQL에 `ORDER BY RANDOM()` 을 쓰지 않는다.** 대신:

- `ORDER BY headword` 로 **안정 정렬**해 반환한다.
- 섞는 것은 호출자(01-06 `Filler`)가 `Random(seed)` 로 한다. 이미 그렇게 설계돼 있다.

## `findByPattern` 구현

```dart
@override
Future<List<WordEntry>> findByPattern({
  required int length,
  Set<int> tiers = const {},
  Map<int, String> fixed = const {},
  Set<String> exclude = const {},
  int limit = 50,
}) async {
  final where = <String>['len = ?'];
  final args = <Variable>[Variable.withInt(length)];

  if (tiers.isNotEmpty) {
    final sorted = tiers.toList()..sort();   // 결정성: 키 순서 고정
    where.add('tier IN (${List.filled(sorted.length, '?').join(',')})');
    args.addAll(sorted.map(Variable.withInt));
  }

  // fixed는 key 오름차순으로 적용 (SQL 텍스트를 안정화 → 준비된 문 캐시 적중)
  final keys = fixed.keys.toList()..sort();
  for (final i in keys) {
    where.add('c${i + 1} = ?');              // 0-based index → c1..c5
    args.add(Variable.withString(fixed[i]!));
  }

  // exclude는 SQL에 넣지 않는다. 아래 "exclude 처리" 참고
  where.add('headword IS NOT NULL');

  final sql = 'SELECT headword, len, tier, pos FROM word '
      'WHERE ${where.join(' AND ')} '
      'ORDER BY headword '
      'LIMIT ?';
  args.add(Variable.withInt(limit + exclude.length));

  final rows = await _db.customSelect(sql, variables: args).get();

  final out = <WordEntry>[];
  for (final r in rows) {
    final hw = r.read<String>('headword');
    if (exclude.contains(hw)) continue;
    out.add(WordEntry(
      headword: hw,
      tier: r.read<int>('tier'),
      pos: r.read<String>('pos'),
    ));
    if (out.length >= limit) break;
  }
  return out;
}
```

### `exclude` 를 SQL에 넣지 않는 이유

> 저가형 기기에서 `NOT IN (...)` 목록이 길어지면 느려짐

그리고 01-06의 질의 캐시가 `exclude` 를 키에서 뺐기 때문에, SQL에 넣으면 **캐시가 안 먹는다.**
격자 안 단어는 수십 개뿐이므로 Dart에서 거르는 비용이 무시할 만하다.
대신 `LIMIT` 를 `limit + exclude.length` 로 늘려 거른 뒤에도 `limit` 개가 남게 한다.

### `c${i + 1}` 인덱스 변환

`fixed` 의 key는 **0-based 음절 index** (01-02 계약), DB 컬럼은 `c1..c5` (1-based).
여기서 off-by-one이 나면 패턴이 한 칸씩 밀려 조용히 틀린 단어가 나온다. 테스트로 못 박는다.

## `coreCandidates` 구현

> `word LEFT JOIN word_stat` → `(correct - wrong*2) ASC`, 동점은 Dart에서 seed 셔플

```dart
@override
Future<List<WordEntry>> coreCandidates({
  required int tier,
  required int count,
  required int seed,
}) async {
  const sql = '''
    SELECT w.headword, w.tier, w.pos,
           COALESCE(s.correct, 0) - COALESCE(s.wrong, 0) * 2 AS score
    FROM word w
    LEFT JOIN word_stat s ON s.headword = w.headword
    WHERE w.tier = ?
    ORDER BY score ASC, w.headword ASC
    LIMIT ?
  ''';

  // 동점 랜덤을 위해 넉넉히 가져온다
  final take = count * 12;
  final rows = await _db.customSelect(sql, variables: [
    Variable.withInt(tier),
    Variable.withInt(take),
  ]).get();

  // 점수별로 묶어 그룹 안에서만 셔플 → 점수 순서는 유지, 동점만 랜덤
  final byScore = <int, List<WordEntry>>{};
  for (final r in rows) {
    byScore.putIfAbsent(r.read<int>('score'), () => []).add(WordEntry(
          headword: r.read<String>('headword'),
          tier: r.read<int>('tier'),
          pos: r.read<String>('pos'),
        ));
  }
  final rnd = Random(seed);
  final out = <WordEntry>[];
  for (final score in byScore.keys.toList()..sort()) {
    final g = byScore[score]!..shuffle(rnd);
    out.addAll(g);
  }
  return out.take(count * 4).toList();
}
```

### 콜드 스타트

처음엔 `word_stat` 이 비어 있어 전부 score 0이다 → 한 그룹 → 전체가 셔플된다.
REVIEW 4.2 (e): "콜드 스타트(전부 0점)는 랜덤으로 자연 처리됨". 의도대로다.

단, `LIMIT count*12` 때문에 **항상 `headword` 사전순 앞쪽 단어만** 후보가 된다.
콜드 스타트에서 `가`로 시작하는 단어만 나오는 문제다. 완화책:

```sql
    ORDER BY score ASC, (w.rowid * 2654435761) % 1000000 ASC
```

`rowid` 해시로 안정적이면서 사전순이 아닌 순서를 만든다. 결정적이고 seed와 무관하다.
**seed별로 다양성이 필요하면** `LIMIT` 를 크게 잡고(예: 2000) Dart에서 셔플 후 자른다.
실데이터 티어당 단어 수(02-10 리포트)를 보고 판단한다.

## 인덱스 사용 확인

```dart
Future<List<String>> explainPattern() async {
  final rows = await _db.customSelect(
    'EXPLAIN QUERY PLAN SELECT headword FROM word '
    'WHERE len = ? AND tier IN (1,2) AND c2 = ?',
    variables: [Variable.withInt(3), Variable.withString('가')],
  ).get();
  return rows.map((r) => r.data.values.join(' ')).toList();
}
```

> `EXPLAIN QUERY PLAN`으로 `(len, tier, cN)` 인덱스가 실제로 잡히는지 확인.
> 잡히지 않으면 인덱스 순서 조정 → `schema.sql` 수정(2단계 산출물 재빌드).

**실기기에서도 확인한다.** 데스크톱 SQLite와 안드로이드 SQLite는 버전이 달라 플래너 판단이 다를 수 있다.

## 막히면

- **인덱스를 안 탐** → `tier IN (...)` 이 범위 조건이라 `(len, tier, cN)` 에서 `cN` 을 못 쓴다. `schema.sql` 을 `(len, cN, tier)` 로 바꾸고 2단계 재빌드. 이게 가장 흔한 원인이다.
- **티어를 1개만 넘길 때는 빠른데 여러 개면 느림** → 위와 같은 원인. 또는 `tiers` 를 `IN` 대신 `tier BETWEEN ? AND ?` 로 바꿀 수 있는지 본다 (레벨 스펙의 티어 집합이 대개 연속이다).
- **결과가 한 칸 밀림** → `c${i + 1}` off-by-one. 테스트가 이미 있어야 한다.
- **콜드 스타트에 `가`로 시작하는 단어만 나옴** → 위 `rowid` 해시 정렬 적용.
- **결정성이 깨짐** → `tiers`/`fixed` 를 정렬하지 않고 SQL을 만들면 `Set`/`Map` 순회 순서에 따라 결과 순서가 달라질 수 있다. 정렬 코드를 확인한다.
- **실기기에서만 느림** → 03-05에서 측정한다. 여기서 추측 최적화하지 않는다.
