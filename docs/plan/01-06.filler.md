# 01-06. 채움 + 백트래킹 (filler)

담당: **AGENT**
선행: 01-05 · 다음: 01-07
상위: [01-domain-map-generator.md](01-domain-map-generator.md) 알고리즘 2번

## 목표

코어가 놓인 격자에 **채움 단어**를 티어별 할당량(`LevelSpec.fillQuotas`)만큼 넣는다.
막히면 되감아(백트래킹) 다른 단어를 시도한다. 되감기 예산을 넘으면 실패를 반환한다.

**1단계에서 두 번째로 까다로운 코드.** 실패율 수치가 대부분 여기서 결정된다.

## 컨텍스트

- 01-01 (`TierQuota`), 01-02 (`findByPattern`), 01-03 (`GridRules`), 01-05 (`Slot`)
- [01-domain-map-generator.md](01-domain-map-generator.md) 리스크 절 — 할당량을 "정확히"가 아니라 "범위"로 두는 완화책

## 알고리즘

```
남은 할당량 remaining = {tier: max} 사본, 달성 최소치 = {tier: min}

재귀 fill(depth):
  if 모든 tier의 달성치 >= min:  성공 반환
  if budget 소진:                실패 반환

  slots = SlotEnumerator.enumerate(g) 를 compareByConstraint 로 정렬
  if slots 비어 있음:            실패 반환

  slot = slots.first                      ← MRV. 가장 제약 강한 슬롯
  tiersWanted = remaining에서 아직 남은 티어 집합
  cands = await repo.findByPattern(
            length: slot.length,
            tiers: tiersWanted,
            fixed: slot.fixed,
            exclude: g.placedWords,
            limit: candidateLimit)        ← 기본 30
  cands 를 Random(seed) 로 셔플

  for w in cands:
    if !GridRules.canPlace(g, w.headword, slot.row, slot.col, slot.dir): continue
    if remaining[w.tier] == 0: continue
    g.place(PlacedWord(..., isCore: false, tier: w.tier))
    remaining[w.tier]--; achieved[w.tier]++
    if fill(depth + 1) == 성공: return 성공
    g.unplace(...)
    remaining[w.tier]++; achieved[w.tier]--
    budget--
    if budget <= 0: return 실패

  // 이 슬롯을 아무 단어로도 못 채움
  budget--
  return 실패
```

### 주의점

1. **슬롯 재열거 비용.** `enumerate` 는 8×8에서 512회 루프라 매 재귀마다 불러도 된다.
   격자가 바뀌면 슬롯이 통째로 달라지므로 캐싱하면 오히려 버그가 난다.
2. **슬롯 하나만 시도한다.** `slots.first` 만 본다. 다른 슬롯은 되감은 뒤 상태가 달라져 자연히 재계산된다.
   모든 슬롯을 for로 도는 구조는 탐색 공간이 폭발한다.
3. **질의 결과 캐시.** 같은 `(length, tiers, fixed)` 조합이 되감기 중 반복된다.
   `Map<String, List<WordEntry>>` 로 fill 호출 1회(= 한 시도) 동안만 캐시한다. 격자가 바뀌어도
   `findByPattern` 결과 자체는 `exclude` 만 다르므로, **exclude를 질의에서 빼고 Dart에서 필터**하면 캐시 적중률이 크게 오른다.
4. **`exclude` 처리.** 위 3번을 따르면 `findByPattern` 에는 `exclude` 를 넘기지 않고,
   반환 리스트에서 `g.placedWords.contains(...)` 를 걸러낸다. 3단계 DB 구현에서도
   `NOT IN` 목록이 길어지는 문제를 피할 수 있다(03-03 리스크).
5. **`limit` 를 크게.** 셔플 후 앞에서부터 쓰므로 `limit` 가 작으면 다양성이 죽는다. 기본 30, 부족하면 스펙에서 올린다.
6. **비동기 재귀.** `Future<bool> fill(int depth) async` 구조. `await` 가 루프 안에 있어도
   더미 구현은 동기 완료라 느리지 않다. 3단계 DB에서는 이 부분이 성능 병목이 된다(03-05에서 측정).

## 산출물

```
app/lib/domain/generator/
└─ filler.dart
```

```dart
import 'dart:math';
import '../model/level_spec.dart';
import '../model/puzzle.dart';
import '../model/word_entry.dart';
import '../repository/word_repository.dart';
import 'grid.dart';
import 'grid_rules.dart';
import 'slot_enumerator.dart';

class FillStats {
  final bool success;
  final int backtracks;
  final int queries;
  final Map<int, int> achieved;   // tier -> 배치 개수

  const FillStats({
    required this.success,
    required this.backtracks,
    required this.queries,
    required this.achieved,
  });
}

class Filler {
  final MutableGrid g;
  final LevelSpec spec;
  final WordRepository repo;
  final Random rnd;
  final int candidateLimit;

  final Map<String, List<WordEntry>> _cache = {};
  late final Map<int, int> _remaining;
  late final Map<int, int> _achieved;
  late final Map<int, int> _minNeeded;
  int _budget;
  int _backtracks = 0;
  int _queries = 0;

  Filler(this.g, this.spec, this.repo, this.rnd, {this.candidateLimit = 30})
      : _budget = spec.backtrackBudget {
    _remaining = {for (final q in spec.fillQuotas) q.tier: q.max};
    _minNeeded = {for (final q in spec.fillQuotas) q.tier: q.min};
    _achieved = {for (final q in spec.fillQuotas) q.tier: 0};
  }

  Future<FillStats> run() async {
    final ok = await _fill();
    return FillStats(
      success: ok,
      backtracks: _backtracks,
      queries: _queries,
      achieved: Map.of(_achieved),
    );
  }

  bool get _quotaMet =>
      _minNeeded.entries.every((e) => _achieved[e.key]! >= e.value);

  Future<List<WordEntry>> _candidates(Slot slot, Set<int> tiers) async {
    final key = '${slot.length}|${tiers.toList()..sort()}|'
        '${(slot.fixed.entries.map((e) => '${e.key}=${e.value}').toList()..sort()).join(',')}';
    final hit = _cache[key];
    if (hit != null) return hit;
    _queries++;
    final r = await repo.findByPattern(
      length: slot.length,
      tiers: tiers,
      fixed: slot.fixed,
      limit: candidateLimit,
    );
    _cache[key] = r;
    return r;
  }

  Future<bool> _fill() async { /* 위 알고리즘 */ }
}
```

### 할당량 초과 허용

`TierQuota.max` 를 넘지 않는 선에서, `min` 만 채우면 성공이다.
격자에 빈 슬롯이 남아 있어도 **할당량을 채웠으면 멈춘다.** 성긴 퍼즐이므로 빈 칸이 남는 게 정상이다.

`app/test/domain/filler_test.dart`

| 테스트 | 기대 |
|---|---|
| 기본 채움 성공 | `FillStats.success == true` |
| 채움 후 `validate` 통과 | errors 비어 있음 |
| 할당량 준수 | 티어별 배치 수가 `[min, max]` 범위 안 |

| 중복 단어 없음 | `placedWords.length == placed.length` |
| 결정성 | 같은 `Random(seed)`, 같은 격자 → 같은 결과 |
| 예산 소진 실패 | `backtrackBudget: 1` 에 빡빡한 할당량 → `success == false` |
| 실패 후 격자 복원 | 실패해도 코어만 남아 있음 (채움은 전부 unplace) |
| 캐시 동작 | `queries` 가 `backtracks` 보다 훨씬 작음 |
| 사전 부족 | 5티어 단어가 0개인 사전에 5티어 할당 → 실패 |

"실패 후 격자 복원" 테스트가 중요하다. 실패 시 `g` 가 코어 상태로 정확히 돌아와야
01-07이 같은 격자로 다른 seed를 시도할 수 있다. 되돌리지 않는 구현이면 01-07에서 매번
`MutableGrid` 를 새로 만들어야 한다 — **그 경우 01-07 문서에 명시한다.**


## 막히면

- **되감기가 폭발해 예산을 항상 소진** → (a) 슬롯 정렬이 MRV로 되는지 확인 (`compareByConstraint` 사용), (b) `candidateLimit` 를 30→60으로, (c) 할당량 `min` 을 낮추고 `max` 를 넓혀 범위로 만든다. 이 셋으로 안 되면 레벨 스펙이 무리한 것이다(01-09).
- **`slots.first` 만 보니 특정 슬롯에서 영영 막힘** → 그 슬롯이 못 채워지면 그 격자는 실패가 맞다. 상위(01-07)가 seed를 바꿔 재시작한다. 여기서 다른 슬롯으로 도망가면 탐색이 폭발한다.
- **캐시 키 충돌** → `fixed` 를 key 오름차순으로 직렬화했는지 확인. `Map.toString()` 은 순서 보장이 없으니 쓰지 않는다.
- **비동기 재귀가 스택 오버플로** → 재귀 깊이는 배치 단어 수(≤ 30)라 문제없다. 오버플로가 나면 되감기에서 깊이가 안 줄고 있다는 뜻.
- **실패 시 격자 복원이 어려움** → 복원 포기하고 01-07이 매번 새 `MutableGrid` + 코어 재배치를 하도록 바꾼다. 비용은 조금 늘지만 안전하다. 바꾸면 01-07 문서도 고친다.
