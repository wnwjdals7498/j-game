## 음절 커버리지를 재는 이유

3단계 격자 생성 실패율의 **선행 지표**다.

- 고유 음절이 많고 각 음절당 단어가 적으면 → 패턴 질의가 자주 빈손 → 실패율 급증
- 채움용 풀(티어 1~3)의 음절 다양성이 특히 중요

REVIEW 4.3: "실패율이 더미보다 크게 높을 것 (실단어는 음절 조합이 성김)".
여기서 숫자를 미리 봐 두면 03-05 결과가 놀랍지 않다.

```sql
-- 티어 1~3 단어에서 각 음절이 몇 개 단어에 나오는가
SELECT ch, COUNT(*) AS n
FROM word_char JOIN word USING (headword)
WHERE tier <= 3
GROUP BY ch ORDER BY n DESC;
```

`n == 1` 인 음절이 많으면 그 음절이 격자에 들어가는 순간 교차가 막힌다.

## `python -m tools check`

리포트와 별개로 **기계가 판정 가능한 것**만 검사해 종료 코드를 낸다. CI(06-06)에서 쓴다.

| 검사 | 실패 조건 |
|---|---|
| 파일 존재 | `words.sqlite` 없음 |

## 눈 검수 절차 (HUMAN)

1. `docs/reports/02-db-report.md` 를 연다.
2. 티어별 샘플 30개씩을 **소리 내어 읽어 본다.** 내가 아는 단어인가?
3. 위 체크리스트 6항목에 답을 적는다.
4. 문제가 있으면 `config.py` 를 고치고 **해당 단계만** 재실행:

| 증상 | 손잡이 | 재실행 |
|---|---|---|
| 1티어에 어려운 단어 | `ADJ_VOCAB` 보정 키우기 | `build --only score` |
| 7티어에 쉬운 단어 | `NO_FREQ_BASE` 낮추기 (1.0 → 0.85) | `build --only score` |
| 고유명사 섞임 | 02-06 F5 구현 보강 | `build --only normalize` 이후 전부 |
| 방언·전문어 섞임 | 02-04 필터 강화 | `build --only parse_stdict` 이후 전부 |
| 뜻풀이 잘림 | `DEFINITION_MAX_CHARS` 올리기 (용량 주의) | `build --only build_sqlite` |
| 부적절한 단어 | `tools/blocklist.txt` 추가 → 02-06 필터에 반영 | normalize 이후 전부 |

`--only` 로 뒤 단계만 돌리면 1~2분이 아니라 몇 초에 끝난다. 이게 파이프라인을 쪼갠 실익이다.

### 부적절한 단어 차단

사전에는 비속어·혐오 표현·성적 표현이 들어 있다. 게임에 나오면 스토어 등급(06-04)과
사용자 신뢰 양쪽에 문제가 된다. `tools/blocklist.txt` (표제어 1줄 1개)를 만들고

## 막히면

- **샘플을 봐도 난이도가 맞는지 모르겠음** → 티어 1과 티어 7을 나란히 놓고 본다. 두 집합이 확연히 다르면 산식은 대체로 맞다. 중간 티어의 미세 조정은 실제 플레이(4단계) 후에 한다.
- **조정할수록 다른 데가 망가짐** → 손잡이를 하나씩만 돌리고 매번 리포트를 다시 뽑는다. 두 개 이상 동시에 바꾸면 원인을 못 찾는다.
- **티어 분포가 비율과 ±2%p 넘게 어긋남** → 02-08의 `bounds` 반올림 문제거나, 동점이 대량(빈도 없는 단어가 전부 1.0)이라 경계가 한 점에 몰린 것이다. 후자면 `NO_FREQ_BASE` 를 낮추거나 tie-break에 `headword` 외에 `len` 을 추가한다.
- **부적절한 단어가 너무 많아 일일이 못 막음** → 외부 한국어 비속어 목록을 `blocklist.txt` 초기값으로 쓰고, 출처와 라이선스를 README에 기록한다.
