## 1. 결론

- **방향은 타당함.** "파이썬은 PC에서 데이터 가공만, 앱은 순수 Dart/Flutter" 구조는 안드로이드 제약을 정확히 반영한 결정이다.
- **바로 막히는 지점은 개발 환경.** 이 PC에 Flutter SDK, Android SDK, JDK가 없다. DESIGN의 1단계(`domain/` Dart 코드)조차 Dart SDK 없이는 시작 불가. 환경 구축을 **0단계**로 앞에 넣어야 한다.
- **설계 문서에 비어 있는 결정이 셋 있다.** 격자 규칙(빽빽한 십자말 vs 성긴 낱말퍼즐), 표제어 품사 범위, 레벨 스펙의 저장 위치. 셋 다 1단계 코드에 직접 영향을 주므로 코딩 전에 정해야 한다. (→ 5절)
- **데이터 확보가 외부 의존.** 국립국어원 사전 전체 내려받기는 회원가입·이용 신청 절차가 있다. 승인 대기 시간이 있을 수 있어 0단계에서 병행 착수해야 한다.

## 2. "파이썬 코드가 로컬에서 돌아가는가" 에 대한 답

질문의 핵심 혼동: *안드로이드 앱을 만드는데 파이썬 코드는 어디서 실행되는가.*

```
[개발 PC]                                       [안드로이드 기기]

python tools/build_db.py                        APK 안에 든 것:
  ├ 사전 XML 읽기                                 ├ Flutter 엔진 (C++)
  ├ 빈도·어휘 결합                                 ├ Dart 코드 → ARM 네이티브로 컴파일된 것
  └ words.sqlite 생성  ───→ app/assets/  ───→     └ assets/words.sqlite (파일 그대로)
                                                 
flutter build apk                               파이썬: 없음. 실행 안 됨. 필요 없음.
  └ Dart 컴파일 + assets 포장 → APK
```

- **파이썬은 이 PC에서 돈다.** Python 3.13.13 설치 확인됨. `sqlite3` 표준 모듈 동작 확인(라이브러리 3.50.4). 추가 패키지 없이도 XML 파싱(`xml.etree`)과 SQLite 생성이 가능하다.
- **파이썬은 기기에서 안 돈다. 돌릴 계획도 없다.** 산출물인 `words.sqlite` 파일 하나만 앱에 들어간다. 앱은 이 파일을 읽기만 한다.
- 두 툴체인은 **파일 하나로만 연결**된다. 파이썬 쪽이 깨져도 이미 만들어진 sqlite가 있으면 앱 빌드는 된다. 반대로 Flutter가 없어도 파이썬 ETL은 지금 당장 개발할 수 있다.
- 주의: 이 PC에서 `python3` 명령은 3.6.8(구버전)을 가리킨다. `python` 또는 `py -3.13` 을 쓸 것. 프로젝트는 venv로 고정.

## 4. DESIGN.md 항목별 검토

### 4.1 타당한 결정 (그대로 진행)

| 항목 | 평가 |
|---|---|
| 단일 프로세스 순수 Dart | 정확. 안드로이드에서 로컬 서버 프로세스 구조는 배포 불가 |
| 파이썬 = 오프라인 ETL | 정확. 2절 참조 |
| Flutter Web + drift wasm으로 테스트 | 가능. 단, 4.2의 웹 저장소 차이 주의 |
| `domain/`이 DB·UI를 모름 | 좋음. 더미 사전 단위 테스트가 이 프로젝트의 핵심 검증 수단 |
| `word` PK = 표제어 문자열, `sense` 분리, `word_stat` 보존 | 좋음. 갱신 시 유저 기록 보존 구조로 적절 |
| 음절 컬럼 `c1..c5` + 자리별 복합 인덱스 | 좋음. 패턴 질의를 인덱스 스캔으로 떨어뜨리는 표준 기법 |
| 7단계 피라미드 분할 | 타당. 등분위 금지 결정 옳음 |
| 빈칸 = 오답 | 타당. 게임 설계 판단 |
| 라이선스 인식 | 정확. 예문·음성·이미지 제외 결정 중요 |
| 진행 순서: 알고리즘 먼저 | 동의. 단, 앞에 환경 구축 단계 필요 |

### 4.2 보완 필요

**(a) 웹과 네이티브의 첫 실행 흐름이 다르다.**
"assets의 시드 DB를 앱 저장소로 복사"는 네이티브 전용. 웹(drift wasm)은 파일 시스템 복사가 없고, DB 바이트를 OPFS 또는 IndexedDB에 적재하는 방식이다. `data/` 계층에서 플랫폼별 초기화 분기가 필요하다. 갱신(SyncService)도 웹에서는 1차 범위 제외가 현실적.

**(b) 표제어 정규화 규칙이 없다.**
사전 표제어에는 동형어 번호(`가다01`), 접사 하이픈(`-이다`), 띄어쓰기(`가게 주인`), 비한글(`PC방`)이 섞여 있다. 격자에 쓸 수 있는 형태는 "한글 완성형 음절 2~5개로만 구성"이다. ETL에 명시적 필터 단계 필요. 1음절 단어도 격자에서 제외(교차 불가).

**(c) 품사 범위 미정.**
"단어"의 범위가 명사만인지, 동사·형용사 기본형(`가다`, `예쁘다`)을 포함하는지에 따라 풀 크기와 힌트 품질이 크게 달라진다. 조사·어미·접사·의존명사·구·속담은 제외 확정. **1차는 명사 중심**을 권고하되 `pos` 컬럼은 남겨 레벨 스펙에서 켜고 끌 수 있게.

**(d) 레벨 스펙의 위치.**
"레벨 스펙 조회"가 DB에서인지 코드에서인지 불명. DB에 넣으면 레벨 튜닝마다 DB를 재빌드해야 한다. **Dart 상수 테이블(또는 JSON asset)** 권고. `domain/`이 `LevelSpec` 타입만 받으면 됨.

**(e) 통계 점수 공식 미정.**
"통계 점수 낮은 순"으로 코어를 뽑는데, 점수 산식(정답/오답 가중, 최근성)이 없다. 초기엔 단순 산식으로 고정하고 `규칙` 절에 기록. 콜드 스타트(전부 0점)는 랜덤으로 자연 처리됨.

**(f) 생성 실패 정의와 측정 방법.**
"백트래킹 + 실패율 계측"을 넣기로 했으나, 실패의 정의(시간 제한? 재시도 횟수?)와 측정 하네스 형태가 없다. 1단계에서 하네스를 만들고 3단계에서 실데이터로 재측정하는 흐름으로 확정.

**(g) 갱신 배포처 미정 → GitHub Releases로 기본 확정 권고.**
무료, 정적 URL, 용량 제한 넉넉. `manifest.json` + sqlite 파일 구조.

### 4.3 리스크 재평가

| 리스크 | DESIGN 인식 | 추가 의견 |
|---|---|---|
| 격자 생성 실패 | 있음 | **격자 규칙에 따라 난이도가 10배 차이.** 5절 (1) 결정이 선행돼야 함 |
| DB 용량 | 있음 | 10MB 목표 현실적. 뜻풀이 1개·80자 컷이면 5만 단어 기준 무리 없음 |
| 라이선스 | 있음 | 앱 내 출처 표기 화면을 UI 단계 산출물로 명시 필요 |
| 데이터 확보 | **없음** | 회원가입·신청·승인 절차. 파일 포맷(XML 구조, xlsx/hwp)도 받아봐야 확정. 0단계 병행 착수 |
| 개발 환경 | **없음** | 3절. Flutter 스택 전무 |
| 한국어 IME 입력 | **없음** | 격자 칸에 음절 단위 입력을 받을 때 시스템 IME의 조합 중 상태 처리가 까다롭다. UI 단계의 주요 기술 리스크 |
| 저사양 기기 성능 | 없음 | 패턴 질의·백트래킹이 데스크톱에서 빠르다고 폰에서도 빠르진 않음. 3단계에서 실기기 측정 |

## 5. 코딩 전에 결정할 것 (1단계 진입 조건)

**(1) 격자 규칙 — 가장 중요.**

| 방식 | 설명 | 생성 난이도 | 권고 |
|---|---|---|---|
| 빽빽한 십자말 (미국식) | 검은 칸 적음. 가로세로 **모든** 2칸 이상 연속이 단어여야 함 | 매우 높음. 한국어 단어 풀로는 실패율 폭증 | ✗ |
| 성긴 낱말퍼즐 (한국 신문식) | 검은 칸 많음. 배치한 단어만 유효. 단, 우연히 붙어 생기는 2칸 이상 연속은 금지 | 중간. 백트래킹으로 감당 가능 | **✓** |

**성긴 방식 채택 권고.** DESIGN의 "붙어있지 않는 단일 단어 최대 1개" 조건과도 자연스럽게 맞는다.

**(2) 품사 범위.** 1차 = 명사(고유명사 제외). `pos` 컬럼 유지.

**(3) 레벨 스펙 위치.** Dart 상수 테이블.

**(4) 단어 길이.** 2~5음절. (DESIGN은 6 이상 제외만 명시. 1음절 제외 추가)

**(5) 통계 점수 산식 (초안).** `score = 정답수 - 오답수 × 2`, 낮은 순 코어 선택. 뒤집기 쉬운 곳(`규칙` 절)에 기록.

## 6. 진행 순서 수정 제안

DESIGN 7절 순서에 두 가지를 더한다.

```
DESIGN:        1 domain → 2 tools → 3 data → 4 ui → 5 sync

수정:   0 env ──┬─→ 1 domain ──┐
        (+데이터  │             ├─→ 3 data ─→ 4 ui ─→ 5 sync ─→ 6 release
         신청)   └─→ 2 tools ───┘
```

- **0단계 추가**: 환경 구축 + Flutter 스켈레톤 + 데이터 이용 신청.
- **1·2단계 병행**: 서로 의존 없음. 1은 Dart만, 2는 Python만 쓴다. 2는 데이터 승인 대기 중에도 스크립트 뼈대는 만들 수 있다.
- **6단계 추가**: 서명·스토어·라이선스 표기. DESIGN에 없던 배포 단계.

각 단계 상세는 `docs/plan/` 참조. 전체 로드맵은 `docs/PLAN.md`.
