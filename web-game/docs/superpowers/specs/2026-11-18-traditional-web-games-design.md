# 전통 보드게임 웹게임 설계

- 작성일: 2026-11-18
- 범위: 공통 플랫폼과 첫 게임(오목). 이후 게임은 게임마다 짧은 설계를 따로 쓴다.
- 상태: 사용자 승인 (2026-11-18)
- 구현 계획: `web-game/docs/superpowers/plans/2026-11-18-platform-and-omok.md`

## 1. 목적

저작권·상표 문제가 없는 전통 보드게임을 하나씩 웹게임으로 만든다. 이번 단계의 용도는 QA(품질 확인)와 기초 테스트이며, 외부 공개 서비스가 아니다.

전통 게임을 고르는 이유: 게임 규칙·진행 방식은 저작권 보호 대상이 아니고(미국 저작권청 Circular 33, 1~2쪽 "Ideas, Methods, and Systems", 2021-03 개정), 오래된 전통 게임은 이름·규칙 모두 권리자가 없다. 현대 상업 게임의 이름·그림·규칙서 문장은 쓰지 않는다.

## 2. 사용자가 정한 것

| 항목 | 내용 |
|---|---|
| 게임 | 전통 게임을 하나씩 웹게임으로 만든다 |
| 로그인 | 로그인 위임(OAuth/OIDC: 다른 서비스 계정으로 로그인하는 표준 방식). 제공자는 구글, 카카오, 네이버, GitHub |
| 대전 방식 | 사람 대 사람, 사람 대 컴퓨터 |
| 컴퓨터 상대의 용도 | QA·기초 테스트 |
| 로그인 구조 | 선택지 C: 실제 OAuth와 QA 테스트 로그인 병행 (4절) |
| 배포 조건 | 도메인과 HTTPS를 쓸 수 없다 |

## 3. 목표·비목표·실패 조건

### 목표

1. QA 담당자가 `http://10.8.0.1:<포트>`로 접속해 QA 테스트 로그인 후, 오목을 컴퓨터와 끝까지 둘 수 있다.
2. 브라우저 두 개(QA 계정 두 개)로 방 코드를 주고받아 사람 대 사람 오목을 끝까지 둘 수 있다.
3. SSH 포트 포워딩(서버 포트를 내 PC의 localhost에 연결하는 방법)으로 `http://localhost:<포트>`에 접속하면 구글 로그인으로 같은 기능을 쓸 수 있다.
4. 새 게임을 추가할 때 공통 부분(로그인, 방, 대국 진행, 기록, 컴퓨터 상대)을 고치지 않고 게임 규칙 모듈과 판 화면만 추가한다.
5. `lint`·`typecheck`·`test`를 통과한다. 컴퓨터 대 컴퓨터 자동 대국으로 규칙 엔진과 대국 흐름을 검증한다.

### 비목표 (이번 범위에서 제외)

- 공개 도메인·HTTPS 배포
- 매칭 대기열, 레이팅·순위, 채팅, 관전, 대국 시간 제한
- 강한 컴퓨터 상대(AI)
- 기보 다시 보기 화면 (수순은 저장만 한다)
- 여러 로그인 제공자 계정을 한 사람으로 묶기
- 오목 렌주 규칙(금수: 흑에게 금지된 수)
- 네이버 로그인 검수 신청 (QA 계정만 로그인하면 된다)

### 실패 조건 (동작해도 실패로 본다)

- QA 테스트 로그인이 환경 변수로 켜지 않았는데도 동작한다.
- 브라우저가 수의 합법 여부나 승패를 최종 판정한다. 최종 판정은 서버만 한다.
- 게임 하나를 추가할 때 공통 코드를 크게 고쳐야 한다.
- 현대 상업 게임의 이름·그림·규칙서 문장을 쓴다.
- OAuth 클라이언트 비밀값이 저장소에 들어간다.

## 4. 제약

- [검증] 구글은 OAuth 리디렉션 URI(로그인 뒤 돌아오는 주소)에 HTTPS와 도메인을 요구하고, IP 주소를 직접 쓸 수 없다. localhost만 예외다. 출처: https://support.google.com/cloud/answer/15549257 (리디렉션 URI 검증 규칙 항목)
- [검증] 구글 로그인 라이브러리 Google Identity Services(GIS)는 FedCM(브라우저 내장 로그인 API)을 내부에서 자동으로 쓴다. 출처: https://developers.google.com/identity/gsi/web/guides/fedcm-migration
- [검증] 카카오 공식 튜토리얼은 테스트용 리다이렉트 URI로 `http://localhost:4000/redirect`를 쓴다. 출처: https://developers.kakao.com/docs/ko/tutorial/sample-test
- [검증] GitHub OAuth 앱은 `redirect_uri`에 포트가 붙은 loopback 주소(내 PC 자신을 가리키는 주소)를 허용하고, `localhost`보다 `127.0.0.1`을 권장한다. 출처: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps ("Loopback redirect urls" 절)
- [검증] 네이버 로그인은 Callback URL을 최대 5개 등록하고, 서비스 URL은 포트 번호와 프로토콜을 구분하지 않는다. 인증 요청에 `state` 값이 필수다. 검수 승인 전에는 로그인할 수 있는 아이디가 제한된다. 출처: https://developers.naver.com/docs/common/openapiguide/appregister.md ("WEB 설정"), https://developers.naver.com/docs/login/devguide/devguide.md ("3.1.4 사전 검수 요청"), https://developers.naver.com/docs/login/api/api.md (인증 요청 변수)
- [검증] 네이버 공식 문서는 `localhost` Callback URL의 허용 여부를 명시하지 않는다. 앱 등록 때 `http://localhost:<포트>/...`로 등록해 첫 로그인으로 확인한다.
- [검증] 개발 서버(ai-cloud-vm)의 열린 웹 포트는 사설 주소 `10.8.0.1`과 `127.0.0.1`뿐이고, 공개 웹 프록시가 없다. 사용 중인 포트: 2202, 3001, 8765, 8790, 18022, 18080, 24282, 24283, 49374 (`ss -ltnp`, 2026-11-18). Docker는 `freellmapi`만 구동 중이다.
- [검증] 서버의 Node.js는 v24.22.2다. Flutter는 PATH에 없다.
- OAuth 클라이언트 ID·비밀값은 사용자가 각 제공자 콘솔에서 발급한다. 저장 위치는 회사 규칙에 따라 `~/docs/.env`이고, 저장소에는 넣지 않는다.
- 전역 규칙: 코드는 `lint`·`typecheck`·`test` 통과 전에는 완료로 보고하지 않는다.

## 5. 검토한 방식 (Approaches)

### 5.1 로그인 구조 — 사용자 선택: C

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 실제 OAuth만 | 모두 SSH 포트 포워딩으로 localhost 접속 | 실제 로그인 흐름 검증 | 접속자마다 SSH 계정·설정 필요 |
| B. QA 테스트 로그인만 | 닉네임으로 로그인, 10.8.0.1 접속 | 설정이 거의 없음 | 실제 로그인 미검증, 도메인이 생기면 다시 작업 |
| **C. 둘 다** | localhost 접속은 실제 OAuth, 10.8.0.1 접속은 QA 테스트 로그인 | 실제 로그인 검증과 여러 명 테스트를 함께 | 로그인 경로 두 개를 구현·테스트 |

C를 고른 이유: QA 목적에는 여러 명이 바로 접속할 수 있어야 하고, 나중에 정식 배포할 때는 QA 로그인만 끄면 된다.

### 5.2 대국 처리 구조 — Claude 판단

| 방식 | 판단 |
|---|---|
| **서버가 판정하는 단일 서버 + WebSocket** (채택) | 서버 하나가 수를 검증하고 상태를 양쪽에 보낸다. WebSocket은 서버와 브라우저가 연결을 유지하며 주고받는 통신이다. QA 재현성과 부정 방지에 유리하다. |
| 브라우저끼리 직접 연결, 서버는 중계만 | 브라우저가 판정하므로 3절 실패 조건에 걸린다. 제외. |
| Firebase·Supabase 같은 외부 백엔드 서비스 | 외부 서비스 계정이 필요하고, 로그인 리디렉션 제약은 그대로다. 개발 서버 안에서 끝나야 하는 QA 용도와 맞지 않는다. 제외. |

## 6. 설계

### 6.1 구성

```text
브라우저 (SPA: 한 페이지에서 화면을 바꾸는 웹앱)
  ├─ 화면: 로그인 · 게임 목록 · 로비 · 대국 · 결과 · 내 기록
  └─ 규칙 엔진(공용) — 합법 수 표시·미리보기용
        │ HTTP(로그인·API·정적 파일) + WebSocket(대국)
서버 (Node.js 24, TypeScript, 단일 프로세스)
  ├─ 로그인: 제공자 플러그인(google · OAuth 코드 흐름 제공자 · qa)
  ├─ 방·대국 관리: 수 검증, 상태 전송, 재접속
  ├─ 컴퓨터 상대(QA 봇)
  ├─ 규칙 엔진(공용) — 최종 판정
  └─ SQLite 파일 DB: 계정 · 대국 · 수순
Docker Compose 서비스 1개, 포트는 127.0.0.1과 10.8.0.1에만 연결
```

- 언어는 서버·브라우저 모두 TypeScript다. 규칙 엔진은 서버와 브라우저가 같은 코드를 쓴다.
- 서버 프로세스는 하나다. QA 용도에는 수평 확장이 필요 없다.

### 6.2 게임 규칙 모듈 계약

게임마다 아래 계약을 구현하는 순수 함수 모듈 하나를 만든다. 순수 함수는 입력이 같으면 결과가 같고, 파일·네트워크·시간에 의존하지 않는 함수다.

```ts
interface GameRules<State, Move, Options = unknown> {
  id: string;                                   // 예: "omok"
  initialState(options: Options): State;
  currentPlayer(state: State): 0 | 1;           // 0 = 선수(오목의 흑)
  isLegal(state: State, move: Move): boolean;
  legalMoves(state: State): Move[];
  applyMove(state: State, move: Move): State;   // 원본 state를 바꾸지 않는다
  outcome(state: State):
    | { kind: "ongoing" }
    | { kind: "win"; winner: 0 | 1 }
    | { kind: "draw" };
}
```

- 수(Move)와 상태(State)는 JSON으로 저장·전송할 수 있어야 한다.
- 기권은 규칙 모듈이 아니라 공통 대국 관리가 처리한다.
- 판 화면은 게임마다 별도 컴포넌트로 만들고, 공통 대국 화면이 끼워 넣는다.

### 6.3 첫 게임: 오목 규칙 — Claude 판단

- 15×15 판의 교차점에 둔다. 흑이 먼저 둔다.
- 가로·세로·대각선으로 같은 색 돌이 5개 이상 연속되면 이긴다(자유 오목, 금수 없음).
- 판이 가득 차면 무승부다.
- 이유: 규칙이 가장 단순해서 공통 플랫폼 검증에 집중할 수 있다. 렌주 규칙은 비목표로 미룬다.

### 6.4 로그인

| 제공자 | 방식 | 켜지는 조건 |
|---|---|---|
| google | GIS "Sign in with Google" 버튼으로 ID 토큰(로그인한 사람 정보가 서명된 문자열)을 받고, 서버가 구글 공개키로 서명을 검증한다 | 구글 클라이언트 ID 환경 변수가 있을 때 |
| kakao, naver, github | 인가 코드 흐름. 모든 요청에 `state`(위조 요청을 막는 일회용 값)를 쓰고, 제공자가 지원하면 PKCE(가로챈 인가 코드를 못 쓰게 하는 장치)도 쓴다. 인가 코드를 토큰으로 바꾸는 일과 클라이언트 비밀값 보관은 서버가 한다 | 해당 제공자 환경 변수가 있을 때 |
| qa | 닉네임을 입력하면 QA 계정을 만들거나 다시 쓴다. 화면에 `QA` 배지를 붙인다 | `QA_LOGIN=1`일 때만 |

- 실제 로그인 접속 주소는 `http://localhost:<포트>` 하나로 통일한다. 쿠키는 주소별로 따로 저장되므로, 제공자마다 `localhost`와 `127.0.0.1`을 섞어 등록하면 로그인 뒤 세션이 끊긴다. 네 제공자 모두 리디렉션 URI를 `localhost` 기준으로 등록한다.
- 화면 표시: 접속 주소가 `localhost`이면 켜진 실제 제공자 버튼을 보인다. 그 밖의 주소(예: `10.8.0.1`)에서는 실제 버튼이 동작하지 않으므로 숨기고 QA 로그인만 보인다.
- 제공자 추가는 제공자 모듈 하나(인가 주소, 토큰 교환, 사용자 정보 조회)와 환경 변수만으로 끝나야 한다.
- 세션: 서버 세션 + 쿠키(`HttpOnly`, `SameSite=Lax`). HTTPS가 없어 `Secure` 속성은 쓸 수 없다. 이 위험은 사설망 QA 용도에서 받아들인다.
- 계정 식별: `(제공자, 제공자의 사용자 ID)` 쌍이 계정 하나다.
- 비밀값: 환경 변수로만 받는다. Docker Compose는 저장소 밖의 env 파일을 참조한다.

### 6.5 화면 흐름

```text
[로그인] ─▶ [게임 목록: 오목 (이후 게임 추가)]
               │
               ▼
          [오목 로비]
            ├─ 컴퓨터와 두기 ── 내 색(흑/백/무작위) · 봇 단계(random/basic)
            ├─ 방 만들기 ──── 방 코드 표시 → 상대 입장 대기
            └─ 방 코드 입력 ── 입장
               │
               ▼
          [대국] 판 · 차례 표시 · 마지막 수 표시 · 기권 · 상대 연결 상태
               │
               ▼
          [결과] 승/패/무 · 다시 하기 · 로비로
[내 기록] 지난 대국 목록(게임, 상대, 결과, 날짜)
```

### 6.6 사람 대 사람

- 방을 만든 사람이 색을 고른다(흑/백/무작위, 기본 무작위). 방 코드는 6자리 영문 대문자·숫자로 하고, 헷갈리는 글자(O·0·I·1)는 뺀다.
- 서버가 차례·합법 여부를 검증한 뒤 양쪽에 새 상태를 보낸다. 잘못된 수는 거부 사유와 함께 돌려보낸다.
- 연결이 끊겨도 대국은 서버에 남는다. 다시 접속하면 현재 상태부터 이어서 둔다. 상대에게는 연결 끊김을 표시한다.
- 시간 제한은 없다(비목표). 진행이 멈춘 대국은 기권으로 끝낸다.

### 6.7 사람 대 컴퓨터 (QA 봇)

- 봇은 서버에서 돌고, 규칙 모듈 계약만 써서 모든 게임에 공통으로 동작한다.
- 단계 두 개:
  - `random`: 합법 수 중 무작위로 둔다. 시드(난수 시작값)를 지정하면 같은 대국을 재현할 수 있다.
  - `basic`: 바로 이기는 수가 있으면 두고, 없으면 상대가 바로 이기는 수를 막고, 그것도 없으면 무작위로 둔다.
- 봇 대 봇 대국을 자동 테스트에 쓴다.

### 6.8 데이터

| 테이블 | 주요 열 |
|---|---|
| users | id, provider, provider_user_id, display_name, is_qa, created_at |
| games | id, game_id(예: omok), mode(pvp/pvc), black_user_id, white_user_id 또는 봇 단계, status, result, room_code, created_at, ended_at |
| moves | game_id, seq, player, move(JSON), created_at |

### 6.9 검증

| 종류 | 내용 |
|---|---|
| 단위 테스트 | 오목 규칙: 가로·세로·두 대각선 5목, 6목 이상 승리, 판 가득 참 무승부, 이미 둔 자리 거부, 차례 위반 거부 |
| 봇 테스트 | 봇 대 봇 다수 대국에서 불법 수 0건, 모든 대국이 승·패·무 중 하나로 종료 |
| 통합 테스트 | 서버를 띄우고 QA 로그인 두 계정으로 방 만들기 → 입장 → 대국 종료. 사람 대 컴퓨터 대국 종료. 재접속 후 상태 유지 |
| 브라우저 E2E | Playwright로 QA 로그인 → 컴퓨터와 오목 한 판 → 결과 화면 |
| 제공자 단위 테스트 | 각 OAuth 제공자 모듈의 인가 주소 생성, `state` 불일치 거부, 토큰·사용자 정보 응답 처리를 가짜 제공자 서버로 검증 |
| 수동 확인 | SSH 포트 포워딩으로 localhost 접속 후 구글·카카오·네이버·GitHub 실제 로그인 (계정이 필요해 자동화하지 않음) |
| 공통 | `lint`·`typecheck`·`test` 통과 |

## 7. 이후 게임 순서 (제안)

오목 → 리버시 → 장기 → 바둑 → 체스. 판과 규칙이 단순한 것부터 붙여 공통 계약을 다듬는다. 게임마다 시작 전에 짧은 설계를 쓴다.
