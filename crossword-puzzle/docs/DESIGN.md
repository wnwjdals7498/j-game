# 단어 연상 퀴즈 — 구현 방향

## 1. 한 줄 요약

국립국어원 사전 데이터를 오프라인 SQLite로 말아서 앱에 동봉하고, 십자말 격자 맵을
기기 안에서 매번 새로 생성하는 Flutter 앱. 인터넷은 6개월마다 단어 갱신할 때만 씀.

---

## 2. 핵심 방향 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 런타임 구조 | **단일 프로세스, 순수 Dart** | 안드로이드에 파이썬 런타임 없음. FastAPI 프로세스를 기기에서 못 띄움 |
| 파이썬 역할 | **오프라인 ETL 전용** (앱에 미포함) | 사전 XML 가공은 빌드 타임 1회. 기기에서 할 이유 없음 |
| 웹 테스트 | Flutter Web + drift wasm | 앱과 **동일 Dart 코드** 그대로 구동. 별도 백엔드 불필요 |
| 사전 원본 | 한국어기초사전(주) + 표준국어대사전(보충) | 기초사전은 학습자용이라 뜻풀이 짧고 깔끔. 표준은 방언·옛말·전문어 범벅이라 필터 비용 큼 |
| 힌트 | 뜻풀이 기본 + 유의어 있으면 연상어 모드 | 추가 데이터 파이프라인 없이 두 모드 확보 |
| 통계 단위 | 단어별 | 틀린 그 단어가 다시 코어로 나와야 복습 효과 |
| 맵 형태 | 십자말 교차 격자 | 스펙의 "~자리에 ~가 포함된 단어", "붙어있지 않는 단일 단어"가 격자 전제 |

## 3. 큰 구조

```
j-game/
├─ tools/        # Python. 오프라인 전용, 배포물 아님
│                #   사전 수집 → 파싱 → 빈도 결합 → 7단계 난이도 → words.sqlite 산출
│
├─ app/          # Flutter. 이게 제품 전부
│  ├─ data/      #   DB 스키마, WordRepository, 갱신(SyncService)
│  ├─ domain/    #   맵 생성기, 난이도 스펙, 채점  ← 순수 Dart, 플랫폼 의존 0
│  └─ ui/        #   격자 화면, 입력, 제출
│
└─ docs/
```

원칙: **`domain/`은 DB도 UI도 모름.** `WordRepository` 인터페이스만 받음.
그래야 맵 생성 알고리즘을 더미 사전으로 단위 테스트할 수 있음.

### 3.1 데이터 파이프라인 (tools/)

```
사전 XML(기초+표준)  ─┐
빈도조사2 (약 6만)    ─┼─→ 정규화 → 복합 점수 → 7단계 분류 → words.sqlite → app/assets/
학습용 어휘(5,965)    ─┘
```

앱은 이 산출물을 **읽기만** 함. XML을 앱이 파싱하는 일은 없음.

### 3.2 앱 런타임 흐름

```
앱 시작
 └→ 최초 실행? → assets의 시드 DB를 앱 저장소로 복사
 └→ 마지막 갱신 6개월 경과 + 인터넷 있음? → 새 DB(또는 패치) 다운로드 → 머지
 └→ 게임 시작
      └→ 레벨 스펙 조회 (격자 크기 / 코어 티어·개수 / 채움 티어별 개수)
      └→ 코어 단어 선택  … 통계 점수 낮은 순, 동점은 랜덤
      └→ 코어들을 교차 배치
      └→ 남은 칸을 저난이도 단어로 채움  … 패턴 질의 + 조건 맞는 것 중 랜덤
      └→ 실패 시 시드 바꿔 재시도 (백트래킹)
 └→ 플레이 → "제출" → 일괄 채점 → 통계 반영
```

## 4. 데이터 모델 방향

갱신이 편하려면 **"게임이 쓰는 것"과 "사전이 주는 것"을 분리**해야 함.

```
word       PK = 표제어 문자열      게임 객체. 음절 컬럼(c1..c5), 난이도 티어, 빈도
sense      PK = 사전 고유 ID        뜻풀이·품사·유의어. word를 참조
word_stat  PK = 표제어 문자열      정답/오답/점수
word_char  역색인                  "~와 ~를 포함한 단어" 질의용
```

이렇게 하면:

- 사전 갱신 = `sense` 통째로 갈아엎기 + `word` 업서트. **`word_stat`은 건드리지 않음**
- 사전사가 ID를 재발급해도 유저 기록 안 날아감
- 동음이의어는 `sense`에서 갈라지고, 게임 답은 `word` 하나로 유지됨

### 난이도 7단계 기준

빈도(주) + 학습용 어휘 등급(보정) + 기초사전 등재 여부 + 음절수/자모 복잡도 패널티.
7등분할 때 **등분위 금지** — 상위 티어를 얇게 가져가는 피라미드 분포로 자름.

### 격자 탐색 성능

음절을 컬럼으로 펼치고(`c1..c5`) `(len, tier, cN)` 복합 인덱스를 음절 자리마다 하나씩.
`?가?` 같은 패턴 질의가 인덱스 스캔으로 떨어짐. 6음절 이상 표제어는 격자에서 제외.

## 5. 임의로 정한 규칙 (뒤집으려면 여기만 고치면 됨)

1단계 진입 조건으로 확정한 7가지 (출처: `REVIEW.md` 5절, `plan/01-01.domain-models.md`).

1. **격자 규칙 — 성긴 낱말퍼즐 방식.** 배치한 단어만 유효.
   우연히 인접해 생기는 2칸 이상 연속은 금지. 검은 칸 개수 제한 없음.
2. **단어 길이 2~5음절.** 1음절 제외(교차 불가), 6음절 이상 제외.
3. **고립 단어(다른 단어와 교차 없음)는 맵당 최대 1개.** 나머지는 전부 하나의 연결 요소.
4. **레벨 스펙은 Dart 상수 테이블** (`app/lib/domain/levels.dart`). DB에 넣지 않는다.
5. **통계 점수 산식 `score = correct - wrong * 2`.** 코어는 낮은 순, 동점 랜덤.
6. **품사 1차 범위는 명사** (고유명사 제외). `pos` 필드는 남겨 확장 가능하게 둔다.
7. **채점 — 빈칸은 오답(-1). 부분 정답 없음.** 재제출은 허용하되 통계는 첫 제출만 반영.
   (빈칸을 오답으로 두지 않으면 어려운 칸을 비워서 점수를 방어함)

그 외:

- 채움 단어 풀은 기초사전만으로 시작. 표준 보충분은 대부분 최하위 티어라 채움용으로 못 씀.
  생성 실패율 측정 후 필요하면 투입
- **`app/assets/words.sqlite` 는 커밋한다** (2단계에서 확정. 출처: `plan/02-09.build-sqlite.md`
  "app/assets 복사"의 권고). 클론만 하면 앱이 빌드된다. 원본 자료는 재배포 불가지만
  파생 DB는 CC BY-SA 2.0 KR로 배포 가능하고, 갱신이 6개월에 한 번이라 저장소 증가가 느리다.
  뒤집으려면 `.gitignore` 에 `app/assets/words.sqlite` 를 넣고, 빌드 전에 항상
  `python -m tools build` 를 돌리는 절차를 `docs/RELEASE.md`(06-05)에 명시한다.
  현재 커밋된 파일은 **`tools/fixtures/` 샘플로 만든 것**이라 실데이터가 아니다
  (00-01 승인 대기). DB 안 `meta.source_versions.origin` 이 `fixtures` 로 그 사실을 말한다.
- **`word_char` 역색인은 현재 어디서도 쓰지 않는다** (03-03 결정, 02-09 "막히면" 절이
  이 판단을 03-03에 위임했다). 근거: `findByPattern`(03-03)은 `(len, tier, cN)`
  인덱스만으로 충분하고(desktop SQLite `EXPLAIN QUERY PLAN` 으로 확인,
  `app/test/data/word_repository_test.dart` "인덱스 사용" 테스트), 4단계 힌트
  명세(`plan/04-03.selection-and-hint.md`)를 포함해 전체 계획 문서를 검색해도
  "~을 포함한 단어" 질의를 쓰는 화면이 없다. 즉 02-09의 "안 쓰면 뺀다" 조건을
  만족한다.
  **다만 지금 스키마에서 즉시 제거하지는 않는다.** 제거하려면 `tools/schema.sql`·
  `build_sqlite.py`(02-09)와 `app/lib/data/db/app_database.dart`(03-01)의
  `WordChars` 테이블·관련 테스트(`schema_contract_test.dart` 등)를 함께 고쳐야
  하는데, 이는 03-03(패턴 질의 구현)의 범위를 벗어나고, 지금 커밋된 DB는 어차피
  00-01 승인 대기 중인 16단어 fixtures 샘플이라 용량 절감 효과를 실측할 수도 없다.
  **실행 시점: 00-01 실데이터가 들어와 02-09를 다시 돌릴 때** 이 결정을 반영해
  `word_char` 를 스키마에서 뺀다(위 파일들 동시 수정). 4단계 진행 중 "포함 단어"
  힌트가 실제로 필요해지면 이 결정을 뒤집고 테이블을 유지한다.

## 6. 제약 / 리스크

- **DB 용량**: 뜻풀이 전체 넣으면 30~60MB. 단어당 뜻풀이 1개·길이 컷으로 ~10MB 목표
- **생성 실패**: 격자가 크고 채움 티어가 좁으면 패턴에 맞는 단어가 없어 막힘.
  백트래킹 + 실패율 계측을 처음부터 넣을 것
- **라이선스**: 사전 데이터 CC BY-SA 2.0 KR → 앱 내 출처 표기, 파생 DB도 동일 조건.
  **인용 예문·음성·이미지는 개방 대상 아님 → 추출 단계에서 제외.**
  빈도조사/학습용 어휘는 공공누리 1유형(출처 표기)
- **갱신 배포처**: 미리 빌드된 sqlite를 어디에 올릴지 미정 (GitHub Releases 등)

## 7. 진행 순서

1. `domain/` 맵 생성기 + 더미 사전으로 단위 테스트 ← **여기부터**
2. `tools/` ETL로 실제 words.sqlite 산출
3. `data/` 연결, 실데이터로 생성 실패율 측정
4. `ui/` 격자 화면
5. 갱신(SyncService)

1번을 먼저 하는 이유: 알고리즘이 이 프로젝트의 유일한 난제이고, 사전 없이도 검증 가능함.
