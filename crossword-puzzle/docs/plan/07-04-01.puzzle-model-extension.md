## 작업

### 1. 진행 계산 게터 2개

`answers` 필드 선언 아래, `selectNextWord` 위에 넣는다.

```dart
/// 모든 칸이 채워진 단어 수. 진행 배지 "n / N"의 n (07-04-03).
/// [textOf]가 중간 빈칸에서 끊기므로 길이 비교만으로 "꽉 참"을 판정할 수 있다.
int get filledWordCount => puzzle == null
    ? 0
    : puzzle!.words.where((w) => textOf(w).length == w.length).length;

/// 격자의 모든 비검은 칸이 채워졌는가. 제출 버튼 E-05의 상태 (07-04-03).
/// 단어 단위가 아니라 **칸 단위**로 센다 — 제출 확인 시트의 빈칸 문구가
/// 같은 `Scorer.blankCellCount`를 쓰므로(04-05), 기준이 어긋나면 "버튼은
/// 기본 스타일인데 시트는 빈 칸이 있다고 말하는" 상태가 생긴다.
bool get allFilled =>
    puzzle != null && Scorer.blankCellCount(puzzle!, answers) == 0;
```

`import '../../domain/scoring/scorer.dart';`는 **이미 파일 맨 위에 있다**(`submit`이 쓴다). 새 import는 필요 없다.

### 2. `selectPrevWord`

`selectNextWord` 바로 아래에 둔다. 두 메서드가 같은 순회 순서(`puzzle.words`)를 공유한다는 게 한눈에 보여야 한다.

```dart
/// 이전 단어로 이동한다 (ClueBar ◀, 07-04-02). [selectNextWord]의 역방향.
/// 미선택이면 `indexWhere`가 -1을 주는데, 그대로 `(i - 1 + n) % n`에 넣으면
/// 끝에서 두 번째가 걸린다 — [selectNextWord]가 미선택에서 첫 단어를 고르는
/// 것과 짝이 맞게 마지막 단어로 분기한다.
void selectPrevWord() {
  if (puzzle == null) return;
  final order = puzzle!.words;
  if (order.isEmpty) return;
  final i = order.indexWhere((w) => _same(w, selected));
  selected = i < 0 ? order.last : order[(i - 1 + order.length) % order.length];
  notifyListeners();
}
```

### 4. 테스트 픽스처 — 왜 새 격자가 필요한가

`word_input_test.dart`의 기존 `_crossPuzzle()`은 2×2 네 칸이 전부 `Cell.filled`인데, 단어 두 개가 (0,0)(0,1)(1,0) 세 칸만 지난다. (1,1)은 어느 단어도 지나지 않으므로 `blankCellCount`가 영원히 1 이상 → `allFilled`가 절대 true가 되지 않는다. `submit_test.dart`의 `_crossPuzzle()`이 같은 이유로 (1,1)을 막아 두었다. 같은 모양의 픽스처를 이 파일에도 추가한다.

```dart
/// `allFilled` 검증용 2×2. 이 파일의 [_crossPuzzle]과 달리 (1,1)을 **검은
/// 칸**으로 둔다 — `Scorer.blankCellCount`는 단어가 아니라 격자 전체를 훑기
/// 때문이다 (submit_test.dart `_crossPuzzle` 주석과 같은 근거).
Puzzle _fullCoverPuzzle() { /* cells: [[filled('사'), filled('과')], [filled('슴'), blocked()]] */ }
```

### 5. 테스트 — `test/ui/word_input_test.dart`

기존 그룹·테스트 이름은 그대로 둔다(INV-08). 새 파일을 만들지 않는 이유: `selectNextWord` 테스트("다음 단어 순환: 마지막 → 첫 번째")가 이미 이 파일에 있고, 역방향 테스트가 그 옆에 있어야 한 쌍으로 읽힌다.

`PuzzleModel — 다음 단어 이동` 그룹에 추가:

| 테스트 이름 | 기대 |
|---|---|
| `이전 단어 순환: 첫 번째 → 마지막` | `selected = words[0]` → `selectPrevWord()` → `words[1]` |
| `이전 단어: 미선택이면 마지막 단어` | `selected = null` → `selectPrevWord()` → `words.last` |
| `다음 ↔ 이전 왕복: 원래 단어로 돌아온다` | `selectNextWord()` 후 `selectPrevWord()` → 원래 인스턴스와 `same` |

`PuzzleModel — 진행 계산` 그룹 신규:

| 테스트 이름 | 기대 |
|---|---|
| `filledWordCount: 입력 없으면 0` | `_crossPuzzle`, `answers = {}` → 0 |
| `filledWordCount: 한 단어 완성 → 1` | `setWordInput(words[0], '사과')` → 1 |
| `filledWordCount: 부분 입력은 세지 않는다` | `setWordInput(words[0], '사')` → 0 |
| `filledWordCount: 교차 셀 공유로 두 단어가 동시에 참` | `_fullCoverPuzzle`에 '사과'+'사슴' 전부 입력 → 2 |
| `allFilled: 빈칸이 있으면 false` | `_fullCoverPuzzle`, 한 칸만 입력 → false |
| `allFilled: 모든 비검은 칸을 채우면 true` | (0,0)(0,1)(1,0) 셋 다 입력 → true |
| `allFilled: puzzle이 없으면 false` | `newModel()`만 만들고 `puzzle` 미할당 → false |

## 막히면

- **`allFilled`가 실 퍼즐에서 절대 true가 안 됨** → 생성기 출력에 단어가 지나지 않는 비검은 칸이 있다는 뜻이다. 01-03 "고립 금지"상 있을 수 없으므로 모델이 아니라 생성기를 의심한다. 다만 07-04는 `lib/domain`을 못 고치므로(N-06), 재현 seed와 격자를 07-08 리포트에 남기고 넘어간다.
- **`selectPrevWord`가 두 칸씩 건너뜀** → `_same`이 표제어가 아니라 위치+방향을 비교한다. 같은 표제어가 두 번 나오지 않으므로(01-03 규칙 6) 문제가 아니다. `indexWhere`가 -1을 돌려주는 경로를 먼저 확인한다.
- **`filledWordCount`가 교차 단어에서 과소 집계** → `textOf`는 중간이 비면 거기서 끊긴다(04-04 "부분 입력 허용"). 의도된 동작이며 바꾸지 않는다 — 진행 배지는 "꽉 찬 단어 수"지 "입력한 글자 수"가 아니다.
