# 05-03. 통계 보존 · 원자 교체 (db_swapper)

담당: **AGENT**
선행: 05-02 · 다음: 05-04
상위: [05-sync.md](05-sync.md) 동작 흐름 뒷부분

## 목표

새 DB로 갈아끼우되 **유저 통계를 한 줄도 잃지 않는다.**
DESIGN 4절의 핵심 설계("`word_stat`은 건드리지 않음")가 여기서 실현된다.

> 사전사가 ID를 재발급해도 유저 기록 안 날아감

## 보존 대상

| 테이블 | 보존 | 이유 |
|---|---|---|
| `word_stat` | ✓ | 유저의 정답/오답 기록 |
| `puzzle_log` | ✓ | 첫 제출 판정(03-04). 안 지키면 재제출이 이중 집계 |
| `word`, `sense`, `word_char`, `meta` | ✗ | 새 DB 것을 쓴다 |

**`puzzle_log` 를 빠뜨리기 쉽다.** 03-04에서 추가한 테이블이므로 이 목록에 반드시 넣는다.

### 새 DB에 없는 단어의 통계

> `headword` 기준. 새 DB에 없는 단어의 stat도 보존

사전 갱신으로 표제어가 빠질 수 있다. 그 단어의 통계를 지우면
나중에 다시 등재됐을 때 기록이 사라진다. **`word` 에 없어도 `word_stat` 행은 남긴다.**

`word_stat.headword` 에 FK가 걸려 있지 않으므로(02-09 스키마) 그냥 들어간다.

## 흐름

```
1. 새 DB 파일(tmp)에 ATTACH로 기존 DB를 붙인다
2. 기존 DB의 word_stat, puzzle_log를 새 DB로 복사
3. DETACH
4. 앱의 기존 DB 연결을 닫는다
5. tmp → words.sqlite 로 rename (원자적)
6. 새 경로로 DB를 다시 연다
```

**복사를 새 DB 쪽에서 한다.** 기존 DB에 ATTACH해서 쓰면 기존 파일을 건드리게 되고,
중간에 실패하면 기존 DB가 손상된다.

## 구현

```dart
// app/lib/data/sync/db_swapper.dart
import 'dart:io';
import 'package:drift/drift.dart';
import 'package:drift/native.dart';

class DbSwapper {
  final AppDatabase Function(File) _open;   // 주입: 테스트 용이성
  final File currentFile;

  static const _preserved = ['word_stat', 'puzzle_log'];

  /// [newDb] 는 검증이 끝난 임시 파일 (05-02).
  /// 성공하면 새로 연 AppDatabase를 반환한다.
  Future<AppDatabase> swap(AppDatabase current, File newDb) async {
    // 1~3. 새 DB에 기존 것을 붙여 통계를 복사
    await _copyStats(newDb, currentFile);

    // 4. 기존 연결을 닫는다. 이걸 안 하면 rename이 실패할 수 있다
    await current.close();

    // 5. 원자 교체
    final backup = File('${currentFile.path}.bak');
    if (await backup.exists()) await backup.delete();
    if (await currentFile.exists()) {
      await currentFile.rename(backup.path);      // 기존 것을 백업으로
    }
    try {
      await newDb.rename(currentFile.path);
    } catch (e) {
      // 롤백: 백업을 되돌린다
      if (await backup.exists()) await backup.rename(currentFile.path);
      rethrow;
    }

    // 6. 새 DB를 연다
    final next = _open(currentFile);
    await next.wordCount;          // 열리는지 즉시 확인

    // 성공했으니 백업 삭제. 실패해도 무해하므로 예외를 삼킨다
    try { if (await backup.exists()) await backup.delete(); } catch (_) {}

    return next;
  }

  Future<void> _copyStats(File target, File source) async {
    final db = AppDatabase(NativeDatabase(target));
    try {
      await db.customStatement(
          "ATTACH DATABASE ? AS old", [source.path]);
      try {
        for (final t in _preserved) {
          // 기존 DB에 그 테이블이 없을 수도 있다 (구 버전에서 올라온 경우)
          final exists = await db.customSelect(
            "SELECT 1 FROM old.sqlite_master WHERE type='table' AND name=?",
            variables: [Variable.withString(t)]).getSingleOrNull();
          if (exists == null) continue;

          await db.customStatement('DELETE FROM main.$t');
          await db.customStatement(
              'INSERT INTO main.$t SELECT * FROM old.$t');
        }
      } finally {
        await db.customStatement('DETACH DATABASE old');
      }
    } finally {
      await db.close();
    }
  }
}
```

### `INSERT ... SELECT *` 의 위험

컬럼 순서가 두 DB에서 같아야 한다. 스키마 버전이 같다는 건 이미 확인했으므로(05-02)
안전하지만, **명시적 컬럼 목록**을 쓰는 게 더 견고하다:

```sql
INSERT INTO main.word_stat (headword, correct, wrong, last_seen)
SELECT headword, correct, wrong, last_seen FROM old.word_stat
```

컬럼을 추가할 때 이 코드도 고쳐야 하지만, 조용히 어긋나는 것보다 낫다.
**`tools/schema.sql` 을 고치면 여기 컬럼 목록도 고친다** (PLAN.md 3절 계약).

### `DELETE FROM main.word_stat` 먼저

새 DB의 `word_stat` 은 ETL이 만든 **빈 테이블**이다(02-09). 그래도 `DELETE` 를 먼저 하는 이유:
릴리스 스크립트의 `verify`(05-01)를 우회한 오염된 DB가 왔을 때를 대비한다.

### `rename` 이 원자적인 조건

같은 파일시스템 안이어야 한다. 임시 파일을 **앱 문서 디렉터리 안**에 만들면 보장된다(05-02).
`Directory.systemTemp` 를 쓰면 다른 파티션일 수 있어 `rename` 이 복사+삭제가 된다.

### 백업 파일

`rename` 사이에 앱이 죽으면 `words.sqlite` 가 없고 `.bak` 만 남는다.
**다음 실행의 부트스트랩(03-02)이 이걸 복구해야 한다:**

```dart
// open_native.dart에 추가
if (!await file.exists()) {
  final backup = File('${file.path}.bak');
  if (await backup.exists()) {
    await backup.rename(file.path);     // 교체 중 죽은 흔적 복구
  } else {
    await _copySeed(file);
  }
}
```

**03-02 문서에 이 내용을 역으로 반영한다.**

## 구현 메모 (골격에서 벗어난 부분)

- **파일**: `app/lib/data/sync/db_swapper.dart`. 생성자는 문서 그대로
  `DbSwapper({required open, required currentFile, seedAsset})` — `open`은
  `(File) => AppDatabase(NativeDatabase(file))`을 주입받는다(테스트 용이성).
- **`_copyStats`를 `_copyPreservedTables`로, 헬퍼를 `_insertPreserved`로
  이름만 바꿨다** — 로직은 문서 그대로(새 DB 쪽에서 ATTACH, 테이블별
  존재 확인 후 DELETE+INSERT, 컬럼 명시).
- **`.bak` 복구는 실제로 `open_native.dart`에 반영했다.** `recoverOrCopySeed
  (file, copySeed)` 공개 함수를 추가해 `openConnection()`이 쓰게 했다 —
  `copySeedIfAbsent`/`copySeedFile`(03-02)와 같은 이유로 `rootBundle`/
  `path_provider` 없이 테스트 가능한 순수 함수로 분리했다. 테스트는
  `test/data/bootstrap_test.dart`에 있다(아래 "테스트" 절 참고 — db_swapper_test.dart가
  아니다, 로직이 사는 곳을 따랐다).
- **"03-02의 스키마 불일치 재적재가 `DbSwapper` 재사용"도 결국 반영했다.**
  처음에는 "`db_bootstrap.dart`(플랫폼 무관 파사드)가 네이티브 전용
  `DbSwapper`를 알게 하려면 새 조건부 import 분기가 필요하다"고 판단해
  미뤘는데, **그 판단이 틀렸다** — 독립 코드 리뷰가 지적한 대로 그 조건부
  import 분기(`open_stub.dart`/`open_native.dart`/`open_web.dart`)는 이미
  있고, `db_bootstrap.dart`는 거기 함수를 하나 더 추가하기만 하면 된다.
  그래서 실제로 연결했다:
  - `open_native.dart`에 `makeReseeder()`를 추가했다 — 문서 디렉터리
    경로로 `DbSwapper`를 만들고 `reseedFromAsset`을 반환한다.
  - `open_web.dart`/`open_stub.dart`의 같은 이름 함수는 `null`을 반환한다
    (갱신은 웹 1차 범위 밖).
  - `db_bootstrap.dart`의 `DbBootstrap.open()`이 `SchemaMismatch`를 잡아
    `makeReseeder()`가 `null`이 아니면 그걸로 재적재하고 다시 `verify`한다.
    `null`이면(웹) 원래 예외를 그대로 던진다.
  **다만 이 조합(`open()`) 자체에는 새 단위 테스트를 추가하지 않았다** —
  `openConnection()`처럼 `rootBundle`/`path_provider`가 필요해 원래도
  테스트 대상이 아니었다(`test/ui/shell_test.dart`가 이미 그렇게 건너뛴다).
  실제로 이 경로가 프로덕션에서 발동하려면 `meta.schema_version`이
  `AppDatabase.expectedSchemaVersion`과 달라야 하는데, 시드 자산과 그 상수가
  같은 빌드에서 나오고 05-02의 `SyncService`도 `schemaVersion`이 다른
  manifest는 애초에 다운로드조차 안 하므로, **지금은 이 경로가 실제로 발동할
  방법이 없다**(v1 정책 그대로) — 그래도 `reseedFromAsset`·`makeReseeder`
  자체는 완성돼 있고(`swap()`을 통해 간접 테스트됨), 필요해지면 바로 쓸 수
  있다.
- **독립 코드 리뷰 2라운드가 `swap()`의 실제 버그를 잡았다: 6단계(새 DB를
  열어 `wordCount` 확인) 실패 시 롤백에서 `_open(currentFile)`이 이미 연
  연결(`opened`)을 닫지 않고 바로 `currentFile.delete()`/`backup.rename()`을
  시도했다.** Windows sqlite는 열린 파일에 `FILE_SHARE_DELETE`를 안 주므로
  이 두 정리 작업이 **조용히(catch로 삼켜져) 둘 다 실패**했고, 결과적으로
  손상된 새 DB가 살아있는 자리를 차지한 채 진짜 통계가 든 `.bak`만 남는
  상태가 됐다 — 그 위에 `.bak` 정리(위 항목)까지 얹히면 다음 실행에서
  `words.sqlite`가 있다는 이유만으로 `.bak`을 지워 **통계가 영구히
  사라졌다.** 고친 것 둘:
  1. 롤백 전에 `await opened?.close()`를 먼저 한다.
  2. `.bak` 정리를 "`words.sqlite`가 있으면 무조건"에서 "`words.sqlite`가
     있고 **실제로 열리며 `word` 테이블을 읽을 수 있을 때만**"으로 좁혔다
     (`open_native.dart`의 `_opensCleanly`) — 롤백 자체가 다시 실패하는
     극단적인 경우까지 대비한 이중 방어다.
  회귀 테스트: `db_swapper_test.dart`의 "새 DB를 연 뒤 wordCount 확인 실패
  → 롤백"(`close()` 누락을 다시 만들면 이 테스트가 실패한다), `bootstrap_test.dart`의
  "손상됐으면 .bak을 지우지 않는다".
- **알려진 한계 (고치지 않고 남겨 둠, 둘 다 지금은 발동 조건이 없거나
  드물다)**:
  1. `swap()`이 4단계(`current.close()`) 이후 어디서든 실패하면, 호출자
     (`SyncService`)가 들고 있던 `db` 필드는 **닫힌 연결**을 계속 가리킨다
     — 롤백이 완벽히 성공해도(디스크상 DB는 무손상) 그 세션은 더 이상 그
     DB를 읽을 수 없다. 05-04 "막히면"이 이미 이 문제의 **성공** 경로
     버전("갱신 완료 후 앱을 다시 시작해 주세요")을 다루기로 했으니, 실패
     경로도 같은 안내로 묶거나 05-04에서 재오픈 로직을 추가한다.
  2. 재적재(`reseedFromAsset`)의 `_copyPreservedTables`는 옛 테이블이
     **존재하는지**만 확인하고 **컬럼 구성**은 확인하지 않는다. 미래에
     `word_stat`/`puzzle_log`의 컬럼 자체가 바뀌는 스키마 버전 올림이
     있으면 하드코딩된 `INSERT`가 깨져 재적재가 실패하고 앱이 못 뜬다 —
     지금은 스키마 버전이 오른 적이 없어 발동하지 않는다. 실제로 그런
     변경이 생기면 `PRAGMA table_info(old.<table>)`로 실제 컬럼과
     교집합만 복사하도록 고쳐야 한다.

## 막히면

- **`rename` 이 "file in use" 로 실패** → 기존 DB 연결이 안 닫혔다. `current.close()` 를 `await` 했는지, 05-02의 sanity check probe도 닫았는지 확인.
- **`ATTACH` 가 실패** → 경로에 한글·공백이 있으면 따옴표 처리가 필요하다. 파라미터 바인딩(`?`)을 쓰면 해결된다. 위 코드가 그렇게 한다.
- **통계가 일부만 복사됨** → `DELETE` 후 `INSERT` 순서 확인. `INSERT OR IGNORE` 를 쓰면 PK 충돌로 조용히 버려진다. 쓰지 않는다.
- **교체 후 앱이 크래시** → 새 DB 연결 후 `wordCount` 를 확인하는 코드가 있는지 본다. 열자마자 검증해야 문제를 조기에 잡는다.
- **`.bak` 이 계속 쌓임** → 성공 후 삭제가 예외로 건너뛰어졌다. 무해하지만 용량을 먹는다. **구현됨**: `open_native.dart`의 `recoverOrCopySeed`가 `words.sqlite`가 있고 **실제로 열릴 때만**(`_opensCleanly`) 오래된 `.bak`을 정리한다 — 존재 여부만 보고 지우면 롤백 자체가 실패한 극단적인 경우에 통계를 영구히 잃을 수 있다(위 "구현 메모" 참고).
- **교체 후 재적재된 새 DB도 sanity check에서 실패함** → `swap()`이 `_open(currentFile)`/`wordCount` 확인에서 실패하면 원본을 되돌린다(백업 복원). 그래도 실패하면(시드 자산 자체가 손상) `DbBootstrap.open()`이 `verify(next)`에서 다시 예외를 던진다 — 이 경우는 빌드가 잘못된 것이라 코드로 복구할 수 없다.
