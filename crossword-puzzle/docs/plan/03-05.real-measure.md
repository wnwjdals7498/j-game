# 03-05. 실데이터 · 실기기 실측

담당: **MIXED** (하네스는 AGENT, 실기기 실행은 HUMAN)
선행: 03-04 · 다음: 03-06
상위: [03-data-layer.md](03-data-layer.md) E절

## 목표

01-10의 측정 하네스를 **실 DB**로 돌려 실패율·속도를 잰다.
이 단계가 3단계의 존재 이유다.

> 실패율이 더미보다 크게 높을 것 (실단어는 음절 조합이 성김). **이 단계의 존재 이유.**

## 두 환경

| 환경 | 용도 | 실행 방법 |
|---|---|---|
| 데스크톱 | 빠른 반복. 스펙 조정 루프 | `dart run tool/measure_real.dart` |
| **실기기** | DoD 판정 | 앱 안 디버그 화면의 "벤치마크" 버튼 |

데스크톱 수치로 스펙을 맞춘 뒤, 실기기에서 최종 확인한다. **DoD는 실기기 기준이다.**

## 데스크톱 하네스 — `tool/measure_real.dart`

01-10의 `MeasureRunner` 를 그대로 쓰고 repository만 바꾼다.

```dart
import 'dart:io';
import 'package:sqlite3/sqlite3.dart';
import 'package:drift/drift.dart';
import 'package:drift/native.dart';
// ...

Future<void> main(List<String> args) async {
  final runs = _intArg(args, '--runs', 1000);
  final dbPath = _strArg(args, '--db', 'assets/words.sqlite');

  // assets를 직접 열면 word_stat에 쓰게 되므로 임시 복사본을 쓴다
  final tmp = File('${Directory.systemTemp.path}/measure_words.sqlite');
  File(dbPath).copySync(tmp.path);

  final db = AppDatabase(NativeDatabase(tmp));
  final repo = DriftWordRepository(db);
  final runner = MeasureRunner(repo);
  // ... 01-10과 동일한 루프 + 리포트 렌더
  // 출력: docs/reports/03-real-failure.md
}
```

**assets 원본을 직접 열지 않는다.** 측정이 `word_stat` 을 건드리면 결과가 달라진다.

## 실기기 벤치마크 화면

4단계 UI 전이라 임시 화면을 만든다. `main.dart` 에 디버그 진입점:

```dart
// app/lib/ui/debug/benchmark_page.dart  (4단계에서 설정 화면 하위로 옮김)
class BenchmarkPage extends StatefulWidget { ... }
```

- 레벨 선택 드롭다운 + "100회 실행" 버튼
- 진행률 표시 (100회는 폰에서 수십 초 걸릴 수 있다)
- 결과: 실패율, p50/p95, 평균 시도·되감기·질의 수
- **결과를 클립보드로 복사** 하는 버튼 → 리포트에 붙여넣기

실기기는 1000회가 너무 오래 걸린다. **레벨당 100회**로 하고, 데스크톱 1000회와 비교해
"실기기가 데스크톱의 몇 배 느린가" 배수를 구한 뒤 데스크톱 수치에 적용해 추정한다.

UI 스레드를 막지 않도록 `await Future.delayed(Duration.zero)` 를 루프에 넣거나
`compute`(Isolate)로 돌린다. **DB 접근이 있어 Isolate는 까다로우니** 전자가 간단하다.

## 측정 순서

1. **데스크톱 1000회** → 실패율이 1%를 크게 넘으면 03-06으로 가서 스펙을 고치고 재측정. 이 루프를 먼저 돌린다.
2. 데스크톱이 통과하면 **실기기 A 100회**.
3. 저가형 기기가 있으면 **실기기 B 100회**.
4. `EXPLAIN QUERY PLAN` 을 실기기에서 확인 (03-03) — 데스크톱과 다를 수 있다.

## 병목 판정 가이드

| 증상 | 원인 | 조치 |
|---|---|---|
| 되감기 폭증, 질의는 적음 | 채움 풀 부족 | 03-06: 채움 티어 범위 확대 |
| 되감기는 비슷, 총 시간만 김 | 질의가 느림 | 인덱스 확인(03-03). 안 타면 schema.sql 수정 → 2단계 재빌드 |
| 질의 수 폭증 | 01-06 캐시 미작동 | `exclude` 가 캐시 키에 들어갔는지 확인 |
| 코어 배치 실패가 많음 | 티어당 단어 부족 | 03-06: 코어 개수 감소 또는 티어 조정 |
| 특정 레벨만 실패 | 그 레벨 스펙 무리 | 03-06: 해당 레벨만 완화 |

## 채움 풀 부족 시 — 표준 보충분 투입

> 기초사전만으로 채움 풀이 부족하면 표준 보충분 투입 (DESIGN 5절). 3단계 실패율 측정 후 판단.

판단 기준:

- 채움 단계 실패(되감기 소진)가 전체 실패의 절반 이상
- 02-10 리포트의 티어 1~3 음절 커버리지가 낮음

투입 방법: 02-04의 표준 필터를 완화(전문어 허용 등) → 재빌드 → 재측정.
**결정과 결과를 이 리포트에 기록한다.**

## 막히면

- **실패율이 20%+** → 놀라지 않는다. REVIEW 4.3이 예고한 상황이다. 03-06에서 레벨 스펙을 실데이터에 맞게 다시 짠다. 알고리즘을 의심하기 전에 스펙을 먼저 의심한다(01-10에서 더미로는 통과했으므로).
- **실기기가 데스크톱의 10배 이상 느림** → 질의가 병목이다. 인덱스 확인이 최우선. 그 다음은 `candidateLimit`(01-06) 축소 — 질의당 반환 행이 줄어든다.
- **벤치마크 화면이 ANR** → 루프에 `await Future.delayed(Duration.zero)` 를 넣어 UI 스레드를 양보한다.
- **측정할 때마다 결과가 다름** → `word_stat` 이 오염됐다. 임시 복사본을 쓰는지 확인.
- **저가형 기기가 없음** → 있는 기기로만 측정하고 리포트에 명시. 에뮬레이터를 저사양 프로필로 만들어 보조 지표로 쓴다.
