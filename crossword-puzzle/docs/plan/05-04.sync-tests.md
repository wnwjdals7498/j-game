## A. 로컬 HTTP 서버 통합 테스트 — DoD 1번

> 통합(데스크톱 또는 에뮬레이터): 로컬 HTTP 서버로 가짜 manifest·DB 제공

`app/test/data/sync/sync_integration_test.dart`

### 테스트 서버

```dart
class FakeReleaseServer {
  late HttpServer _server;
  late File dbFile;
  Manifest? manifest;
  bool corruptChecksum = false;
  bool cutConnection = false;

  Future<String> start() async {
    _server = await HttpServer.bind(InternetAddress.loopbackIPv4, 0);
    _server.listen((req) async {
      if (req.uri.path.endsWith('manifest.json')) {
        req.response
          ..headers.contentType = ContentType.json
          ..write(jsonEncode(_manifestJson()));
        await req.response.close();
      } else if (req.uri.path.endsWith('.sqlite')) {
        final bytes = await dbFile.readAsBytes();
        if (cutConnection) {
          req.response.add(bytes.sublist(0, bytes.length ~/ 2));
          await req.response.close();     // 절반만 주고 끊는다
        } else {
          req.response.add(bytes);
          await req.response.close();
        }
      } else {
        req.response.statusCode = 404;
        await req.response.close();
      }
    });
    return 'http://127.0.0.1:${_server.port}';
  }
}
```

`SyncService._manifestUrl` 을 **주입 가능하게** 만들어 테스트에서 이 서버를 가리키게 한다.
상수로 하드코딩하면 테스트할 수 없다 — 05-02 구현 시 생성자 인자로 받도록 한다.

**"기존 DB 무손상"의 검증 방법**: 실패 후 기존 DB로 퍼즐을 생성해 본다.
파일 존재 확인만으로는 부족하다 — 반쯤 덮인 파일도 존재는 한다.

```dart
Future<void> expectDbHealthy(AppDatabase db) async {
  expect(await db.wordCount, greaterThan(0));
  final gen = GridGenerator(DriftWordRepository(db));
  final o = await gen.tryGenerate(levels[0], 1);
  expect(o.puzzle, isNotNull);
}
```

**구현 메모**: `expectDbHealthy`는 실제로 `GridGenerator.tryGenerate`까지는 안 한다.
`DriftWordRepository.findByPattern`으로 실 쿼리가 되는지만 확인한다 — 이 테스트의
fixture DB는 db_swapper_test.dart와 같은 최소 단어 2~3개짜리라, 퍼즐 생성에 필요한
다양한 음절·티어 조합이 없어 `tryGenerate`가 fixture 크기와 무관하게 실패할 수 있다.
"파일 존재만으로는 부족하다"는 취지(반쯤 덮인 파일은 쿼리도 안 된다)는 그대로 지켰다
— 전체 퍼즐 생성 검증은 실 `assets/words.sqlite` 기준으로 이미 `levels_test.dart`가
한다.

`app/test/data/sync/sync_integration_test.dart`에 필수 4종 + 추가 10종
(5~14번, 15번은 아래 이유로 제외) = 14개로 구현했다. `FakeReleaseServer`는 문서
그대로 실제 `HttpServer.bind(loopbackIPv4, 0)`을 쓰고, `SyncService`도 진짜
`NativeSyncService`, DB 교체도 진짜 `DbSwapper`를 쓴다 — 05-02/05-03이 처음으로
실제로 맞물려 도는 테스트다. 15번("교체 중 크래시 시뮬레이션 → 부트스트랩이 복구")은
여기 없다 — 그 로직(`recoverOrCopySeed`)이 `data/db/open_native.dart`에 있어
`bootstrap_test.dart`가 이미 직접 검증했다(05-03 "구현 메모").

막힌 것 하나: 순수 `package:test`(flutter_test 아님) 환경엔 Flutter 바인딩이 없어
`NativeSyncService`의 기본 `connectivity`(`Connectivity().checkConnectivity`)가
"Binding has not yet been initialized" 로 즉시 던진다 — `sync_service_test.dart`
처럼 가짜 `connectivity` 콜백을 주입해서 피한다.

## C. 실제 GitHub Releases 검증 (HUMAN) — DoD 2번

> 실기기에서 실제 GitHub Releases의 테스트 릴리스로 갱신 1회 성공, 통계 보존 확인

### 절차

1. `config.DB_VERSION` 을 +1 하고 ETL 재빌드 (02-02, 02-09)
   - 내용을 조금 바꿔 둔다 (예: 단어 10개 추가) → 갱신이 실제로 반영됐는지 확인용
2. `python tools/release_db.py --db tools/build/words.sqlite --out tools/build/release --upload`
3. 브라우저에서 `https://github.com/<owner>/<repo>/releases/latest/download/manifest.json` 접속 → JSON이 보이는지 확인
4. 실기기 앱에서 **통계를 만든다**: 퍼즐 2~3판을 풀고 제출 (`word_stat` 에 행이 쌓임)
5. 설정 → "지금 갱신" 탭
6. 확인:
   - [ ] "단어 N개로 갱신했습니다" 표시
   - [ ] 설정 화면의 DB 버전이 새 값
   - [ ] 단어 수가 새 값
   - [ ] **홈 화면의 누적 통계가 그대로** (보존 확인)
   - [ ] 레벨 클리어 표시가 그대로 (`puzzle_log` 보존 확인)
   - [ ] 다시 퍼즐을 생성해도 정상
7. 앱을 껐다 켜서 새 DB가 유지되는지 확인

### 통계 보존을 정확히 확인하려면

갱신 전후로 홈 화면의 "푼 단어 N개" 숫자를 적어 둔다. **같아야 한다.**
줄었으면 05-03의 보존 로직이 깨진 것이다.

### 테스트 릴리스 정리

확인이 끝나면 테스트 릴리스를 지운다:

```powershell
gh release delete db-v<N> --repo <owner>/<repo> --yes
```

다음 실제 릴리스에서 같은 `db_version` 을 쓸 수 있게 한다.

## D. 설정 화면 연결 — DoD 3번

> 설정 화면에 DB 버전·마지막 갱신일·수동 갱신 버튼 노출

04-06에서 만든 비활성 UI를 실제로 연결한다.

| 요소 | 동작 |
|---|---|
| DB 버전 | `meta.db_version` |
| 단어 수 | `meta.word_count` |
| 마지막 갱신 | `shared_preferences` 의 `last_sync_at` (없으면 "-") |
| 지금 갱신 | `sync(force: true)`, 진행 중 스피너, 결과 스낵바 |
| Wi-Fi에서만 갱신 | `SettingsModel.wifiOnlySync` 토글 |

**구현 메모**: 전부 `settings_page.dart`에 연결했다.

- `_DbInfoSection`은 원래 `last_sync_at`도 `db.metaValue()`(= `meta` 테이블)에서
  읽고 있었다 — 05-02가 진작 지적한 실수(그 값을 `meta`에 두면 DB 교체 때
  사라진다)를 04-06이 남긴 그대로였다. `shared_preferences`(`lastSyncAtPrefsKey`)
  에서 읽도록 고쳤다. 저장 형식이 epoch milliseconds(`int`)라 기존 `_formatDate`
  (ISO 문자열 전용)를 못 쓰고 `_formatEpochMillis`를 새로 만들었다.
- "지금 갱신"은 `_SyncNowButton`(새 `StatefulWidget`)으로 뺐다 — 로딩 상태와
  스낵바를 다루려면 상태가 필요했다. **진행률(다운로드 %)은 구현하지 않았다** —
  `onProgress`가 `NativeSyncService` 생성자 인자라 매 호출마다 값이 바뀌는
  걸 UI에 실시간으로 흘리려면 `ValueNotifier` 같은 별도 상태 배선이 필요한데,
  버튼 비활성화 + 스피너만으로도 "갱신 중" 자체는 충분히 전달된다고 보고
  뒤로 미뤘다. `AppScope.syncService`가 `null`이면(웹) 버튼 자체를 안 그린다.
- 성공해도 `_DbInfoSection`의 DB derived 값(버전/단어 수/빌드 시각)은
  새로고침하지 않는다. **처음엔 이걸 "옛 값이 보인다" 정도로 여겼는데
  틀렸다** — 독립 리뷰가 CRITICAL로 잡아낸 것: 05-03 `DbSwapper.swap`이
  교체 도중 `current.close()`로 **`AppScope.db`를 실제로 닫는다.** 그
  db를 쓰는 모든 것(`HomeModel`, `PuzzleModel.submit`, `_DbInfoSection`)이
  재조회하면 예외를 던진다 — 재시작 안내를 무시하고 계속 쓰면 홈 화면이
  영원히 로딩 스피너에 머물거나(구제 안 됨), 방금 푼 퍼즐의 제출이 아무
  설명 없이 사라질 수 있었다. 고친 것:
  - `HomeModel.load()`/`PuzzleModel.submit()`을 try/catch로 감쌌다.
    `HomeModel`은 `error` 필드를 두고 `HomePage`가 그걸 보면 "다시
    시작해 주세요" 화면을 보여준다(무한 스피너 대신). `PuzzleModel.submit`
    은 실패해도 `submitted`/`result`를 세우지 않는다 — `_handleSubmit`
    (puzzle_page.dart)이 `result == null`을 이미 "계속 풀기"로 처리하므로
    결과 화면으로 잘못 넘어가지 않고, 대신 다이얼로그로 원인을 알린다.
  - `_DbInfoSection`은 이제 `snapshot.hasError`를 본다 — DB 조회가
    실패하면 "-"로 조용히 넘기지 않고 안내 문구를 보여준다. `last_sync_at`
    (shared_preferences)은 DB와 무관하므로 **별도 `FutureBuilder`로
    분리**해 DB 실패와 무관하게 항상 표시된다.
  - **자동 갱신(아래)이 특히 문제였다** — 성공해도 스낵바를 못 띄우므로
    사용자는 아무 경고 없이 위 상태를 만날 수 있었다. `pendingSyncNoticePrefsKey`
    (shared_preferences)를 추가해, 자동 갱신 성공 시 `true`로 세우고
    `HomePage`가 다음 진입 때 그 값을 보고 "다시 시작해 주세요" 스낵바를
    한 번 띄운 뒤 지운다.
  이걸로 최악의 경우(크래시·무한 로딩·조용한 데이터 유실)는 "명확한 안내 +
  재시작 요청"으로 낮췄지만, **재시작을 안내한다고 강제하지는 못한다** —
  이 세션이 계속 열려 있는 한 위 가드들이 계속 방어해야 한다는 뜻이다.
  더 근본적인 해법(`AppScope`를 재구독 가능하게 바꾸거나, 자동 갱신은
  파일만 받아 두고 다음 실행에 적용하는 것)은 여전히 1차 범위 밖이다.
- **재진입 방지**: `NativeSyncService.sync()`에 `_inFlight` 가드를 추가했다.
  없으면 앱 시작 자동 갱신과 "지금 갱신" 버튼이 동시에 겹칠 때 같은 임시
  파일(`words.sqlite.download`)·같은 `words.sqlite`/`.bak`을 동시에 건드릴
  수 있었다(05-04 리뷰 HIGH). 진행 중에 또 불리면 새로 시작하지 않고 먼저
  시작된 호출의 결과에 합류한다.
- `main.dart`의 `_bootstrap()`이 앱 시작 시 자동으로 `sync()`를 한 번
  던진다(05-02 DoD "앱 시작을 막지 않음", `unawaited`). 성공해도 스낵바는
  그 자리에서 못 띄운다(위젯 트리가 없다) — 위 `pendingSyncNoticePrefsKey`로
  다음 화면에 넘긴다.
- 웹에서 `SyncService` 타입 자체를 참조할 수 있어야(`AppScope.syncService`
  필드) 해서 `SyncService`(추상)와 `NativeSyncService`(구현, dart:io 사용)로
  나눴다 — `sync_result.dart`(플랫폼 무관)에 인터페이스를, `sync_service.dart`
  (네이티브 전용)에 구현을 뒀다. `data/db/open_native.dart`/`open_web.dart`/
  `open_stub.dart`에 `makeSyncService()`를 추가해 이미 있던 조건부 import
  분기(`makeReseeder`와 같은 자리)로 만든다 — 웹/스텁은 `null`.
  `flutter build web`으로 실제 컴파일까지 확인했다.
- `skippedSchemaIncompatible`의 스낵바 메시지를 `skippedAppTooOld`와 같은
  "앱을 업데이트해 주세요"로 옮겼다 — 원래 "나중에 다시 시도해 주세요"
  버킷에 있었는데, 스키마 불일치는 재시도로 풀리지 않는 문제라 그 안내가
  거짓이었다(05-04 리뷰 MEDIUM).
- `test/ui/home_settings_test.dart`에 "지금 갱신" 그룹을 추가했다 —
  `syncService == null`일 때 버튼이 안 보이는지, 성공/스키마 불일치 각각
  스낵바 문구가 맞는지, Wi-Fi 토글이 저장되는지. 05-04를 처음 구현했을 때는
  이 화면 쪽에 테스트가 전혀 없었다(05-04 리뷰 HIGH) — 섹션 A(통합 테스트
  14종)만 있고 섹션 D(화면 연결)는 수동 확인에만 기대고 있었다.

갱신 중에는 버튼을 비활성화한다(진행률 %는 위 이유로 생략).

## 막히면

- **`_manifestUrl` 이 상수라 테스트 불가** → **해소됨.** 05-02가 이미 생성자 인자 (`manifestUrl`, 기본값이 실제 URL)로 만들어 뒀다.
- **로컬 서버 테스트가 CI에서 실패** → 포트 바인딩 문제다. `bind(..., 0)` 으로 자동 포트를 쓰는지 확인 — `sync_integration_test.dart`가 그렇게 한다. 이 저장소엔 아직 CI 자체가 없다(`.github/workflows` 없음).
- **"기존 DB 무손상" 테스트가 통과하는데 실기기에서 깨짐** → 파일 잠금 동작이 데스크톱과 안드로이드가 다르다. 실기기에서 다운로드를 끊어(비행기 모드) 재현한다. (HUMAN, B절)
- **갱신 후 통계가 사라짐** → 05-03의 `_preserved` 에 `puzzle_log` 가 있는지, `INSERT ... SELECT` 가 실행됐는지 로그로 확인. `sync_integration_test.dart` 1번·14번이 이 경로를 실제 HTTP+실제 DbSwapper로 돈다.
- **`gh release create` 가 실패** → `gh auth status` 확인. 저장소 권한이 없으면 사람에게 넘긴다. (HUMAN, C절)
- **갱신이 성공했는데 앱이 옛 DB를 봄** → **정정: "옛 DB를 본다"가 아니라 "DB가 닫혀서 예외가 난다"다.** `DbSwapper.swap`이 교체 도중 기존 연결을 `close()`하므로(05-03), `AppScope.db`를 그대로 쓰는 화면은 재조회 시 전부 예외를 만난다. 재구독 가능하게 바꾸는 대신 재시작 안내(`_SyncNowButton`의 성공 스낵바, 자동 갱신의 `pendingSyncNoticePrefsKey`)로 1차 범위를 잡았고, 그사이 세션이 계속 열려 있어도 크래시·무한 로딩·조용한 데이터 유실이 나지 않도록 `HomeModel`/`PuzzleModel.submit`/`_DbInfoSection`에 가드를 넣었다(위 "D. 설정 화면 연결 — 구현 메모" 참고, 05-04 리뷰 CRITICAL).
