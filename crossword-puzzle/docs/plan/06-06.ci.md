## 목표

push마다 자동으로 검사를 돌려 회귀를 잡는다.

> GitHub Actions: push 시 `dart analyze`, `dart test`, `flutter build apk --debug`.
> **서명 빌드는 로컬에서.**

서명 키를 CI에 올리지 않는다. 릴리스는 로컬에서만 한다(06-02).

## 이 단계를 건너뛸 수 있는가

**건너뛸 수 있다.** 06-release.md가 "선택"으로 표시했다.

건너뛰면 잃는 것: 커밋마다의 회귀 감지. 혼자 개발이고 릴리스 전에 06-03의 점검을 하므로
치명적이지 않다. 다만 **DB 재빌드 후 앱 테스트가 깨지는 것**을 늦게 발견하게 된다.

## A. Flutter 검사

`.github/workflows/ci.yml`

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  flutter:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: app
    steps:
      - uses: actions/checkout@v4

      - uses: subosito/flutter-action@v2
        with:
          channel: stable
          cache: true

      - run: flutter pub get

      # 생성물은 커밋돼 있지만(03-01), 소스와 어긋났는지 확인한다
      - run: dart run build_runner build --delete-conflicting-outputs
      - name: 생성물이 최신인지 확인
        run: git diff --exit-code lib/data/db/app_database.g.dart

      # 07-01: UI-GUIDE 7절 불변 조건. PR에서는 base와의 diff로 INV-07까지 본다.
      - run: dart run tool/check_invariants.dart --git-base origin/${{ github.base_ref || 'main' }}

      - run: dart analyze --fatal-infos

      - run: flutter test

      - run: flutter build apk --debug
```

### `words.sqlite` 문제

CI에 `app/assets/words.sqlite` 가 있어야 빌드·테스트가 된다.

- **커밋했다면**(02-09 권고) 그대로 동작한다
- **커밋 안 했다면** CI가 DB를 만들 수 없다 (원본 자료가 없으므로)
  → `app/assets/words.sqlite` 가 없을 때 건너뛰는 테스트로 표시하거나,
     소형 fixture DB를 커밋해 테스트용으로 쓴다

**02-09에서 커밋하기로 결정했으면** 이 문제는 없다.

### `domain/` 플랫폼 import 검사

1단계 내내 수동으로 돌리던 검사를 CI에 넣는다:

```yaml
      - name: domain 계층 격리 확인
        run: |
          if grep -rE "dart:io|package:flutter|package:drift" lib/domain/; then
            echo "domain/에 플랫폼 import가 있습니다"
            exit 1
          fi
```

## B. Python 검사

```yaml
  tools:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.13'
      - run: pip install -r tools/requirements.txt
      - run: python -m pytest tools -q
```

ETL 테스트는 fixture로 돌아가므로(02-01) 원본 자료 없이 통과한다.

## C. 계약 검사

여러 문서가 "두 곳을 같이 고쳐라" 라고 말한다. CI가 강제할 수 있는 것들:

```yaml
      - name: LICENSES.md 동기화 확인
        run: diff docs/LICENSES.md app/assets/LICENSES.md

      - name: manifest 샘플 동기화 확인
        run: diff tools/fixtures/manifest_sample.json app/test/fixtures/manifest_sample.json
```

`tools/schema.sql` ↔ drift 스키마 일치는 03-01의 계약 테스트가 담당한다.
그 테스트가 `assets/words.sqlite` 를 필요로 하므로 위 "words.sqlite 문제" 와 같은 조건이다.

## D. 실패율 회귀 검사 (선택의 선택)

01-10의 하네스를 CI에서 돌리면 알고리즘 회귀를 잡을 수 있다.

```yaml
      - name: 더미 사전 실패율
        run: dart run tool/measure.dart --runs 100
```

`--runs 100` 이면 수십 초다. 1000회는 CI에 너무 길다.
`exit(1)` 이 이미 들어 있으므로(01-10) 실패율이 1%를 넘으면 CI가 빨개진다.

**표본이 작아 노이즈가 있다.** 100회에서 1% 기준은 "1번만 실패해도 실패" 라 예민하다.
CI용으로는 기준을 느슨하게(3%) 두거나, 이 잡을 `continue-on-error: true` 로 둔다.

## E. 캐시

```yaml
      - uses: subosito/flutter-action@v2
        with:
          channel: stable
          cache: true          # Flutter SDK 캐시
```

pub 패키지는 `flutter-action` 이 함께 캐시한다.
Gradle 캐시를 추가하면 APK 빌드가 빨라진다:

```yaml
      - uses: gradle/actions/setup-gradle@v4
```

## F. 하지 않을 것

| 항목 | 이유 |
|---|---|
| 서명 빌드 | 키를 CI에 올리지 않는다 (06-02) |
| Play 자동 업로드 | 사람이 검토하고 올린다 |
| ETL 전체 실행 | 원본 자료가 없고, 있어도 재배포 불가 |
| 실기기 테스트 | 에뮬레이터는 느리고 불안정하다. 로컬에서 한다 |

## 막히면

- **`flutter build apk` 에서 `words.sqlite` 없음** → 02-09의 커밋 결정을 확인한다. 커밋 안 했으면 이 스텝을 빼거나 fixture DB를 쓴다.
- **`build_runner` 결과가 매번 다름** → drift 버전이 CI와 로컬에서 다르다. `pubspec.lock` 을 커밋하고 `flutter pub get` 대신 `flutter pub get --enforce-lockfile` 을 쓴다.
- **CI가 느림 (10분+)** → Gradle 캐시를 추가한다. 그래도 느리면 APK 빌드를 `main` push에만 돌리고 PR에서는 analyze·test만 한다.
- **실패율 검사가 자주 빨개짐** → 표본이 작아서다. `continue-on-error: true` 로 두고 경고로만 쓴다.
- **시간이 없음** → 건너뛴다. 06-release.md가 선택으로 표시한 이유다. 대신 `docs/RELEASE.md` 의 점검 단계를 빠뜨리지 않는다.
