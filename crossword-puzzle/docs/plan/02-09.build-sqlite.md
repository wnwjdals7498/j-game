## 목표

`scored.jsonl` → `tools/build/words.sqlite`. 이 파일이 앱에 동봉되는 **최종 산출물**이다.

`tools/schema.sql` 은 **3단계 drift 스키마와 1:1 대응하는 단일 진실**이다 (PLAN.md 3절 계약).
여기 바뀌면 03-01과 05-03도 같이 바뀐다.

## `tools/schema.sql`

```sql
-- 게임이 쓰는 단어. PK = 표제어 문자열 (DESIGN 4절)
CREATE TABLE word (
  headword  TEXT PRIMARY KEY,
  len       INTEGER NOT NULL,
  c1 TEXT NOT NULL, c2 TEXT NOT NULL, c3 TEXT, c4 TEXT, c5 TEXT,
  tier      INTEGER NOT NULL,          -- 1..7
  pos       TEXT NOT NULL,
  freq_rank INTEGER,
  source    INTEGER NOT NULL           -- bit: 1=기초, 2=표준
);

-- 패턴 질의용 복합 인덱스. 음절 자리마다 하나 (DESIGN 4절)
CREATE INDEX idx_word_c1 ON word(len, tier, c1);
CREATE INDEX idx_word_c2 ON word(len, tier, c2);
CREATE INDEX idx_word_c3 ON word(len, tier, c3);
CREATE INDEX idx_word_c4 ON word(len, tier, c4);
CREATE INDEX idx_word_c5 ON word(len, tier, c5);

-- 사전이 주는 것. 갱신 시 통째로 갈아엎는다
CREATE TABLE sense (
  sense_id   TEXT PRIMARY KEY,         -- 출처 접두어 포함
  headword   TEXT NOT NULL REFERENCES word(headword),
  definition TEXT NOT NULL,
  synonyms   TEXT,                     -- 쉼표 구분. 없으면 NULL
  source     INTEGER NOT NULL
);
CREATE INDEX idx_sense_headword ON sense(headword);

-- "~와 ~를 포함한 단어" 역색인
CREATE TABLE word_char (
  ch       TEXT NOT NULL,
  headword TEXT NOT NULL,
  PRIMARY KEY (ch, headword)
);

-- 앱이 쓴다. ETL은 빈 테이블만 만든다. 갱신 시 보존 대상 (05-03)
CREATE TABLE word_stat (
  headword  TEXT PRIMARY KEY,
  correct   INTEGER NOT NULL DEFAULT 0,
  wrong     INTEGER NOT NULL DEFAULT 0,
  last_seen INTEGER
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

### `meta` 에 넣을 키

| key | 값 | 쓰는 곳 |
|---|---|---|
| `schema_version` | `config.SCHEMA_VERSION` | 03-02 부트스트랩, 05-02 호환성 |
| `db_version` | `config.DB_VERSION` | 05-01 manifest 비교 키 |
| `built_at` | ISO8601 UTC | 리포트·설정 화면 |
| `word_count` | 단어 수 | 05-02 sanity check |
| `source_versions` | 원본 자료 버전/날짜 JSON | 재현성 |
| `license_notice` | `docs/LICENSES.md` 요약 문자열 | 04-06 출처 표기 화면 |

`license_notice` 를 DB에 넣는 이유: 갱신(05)으로 DB만 바뀌어도 출처 표기가 따라가야 한다.

### `word_stat` 을 여기 만드는 이유

앱이 나중에 `CREATE TABLE IF NOT EXISTS` 하는 것보다, 시드 DB에 빈 테이블로 있는 게
스키마 검증(03-01 DoD 5)이 단순하다. 05-03의 `ATTACH` + 복사도 테이블 존재를 전제한다.

## `build_sqlite.py`

```python
import json
import sqlite3
from datetime import datetime, timezone
from . import config, io_util

OUT = "words.sqlite"

def run(use_fixtures: bool = False) -> int:
    dst = config.BUILD / OUT
    if dst.exists():
        dst.unlink()                      # 항상 새로 만든다 (재현성)

    schema = (config.ROOT / "tools" / "schema.sql").read_text(encoding="utf-8")
    con = sqlite3.connect(dst)
    try:
        con.executescript(schema)

        rows = list(io_util.read_jsonl(config.BUILD / "scored.jsonl"))
        rows.sort(key=lambda r: r["headword"])    # 삽입 순서 고정 (재현성)

        con.executemany(
            "INSERT INTO word (headword, len, c1, c2, c3, c4, c5,"
            " tier, pos, freq_rank, source) VALUES (?,?,?,?,?,?,?,?,?,?,?)",
            [_word_row(r) for r in rows],
        )

        sense_rows, char_rows = [], []
        for r in rows:
            for s in r["senses"]:
                sense_rows.append((
                    s["sense_id"], r["headword"],
                    s["definition"][: config.DEFINITION_MAX_CHARS],
                    ",".join(s["synonyms"]) or None,
                    s["source"],
                ))
            for ch in set(r["syllables"]):
                char_rows.append((ch, r["headword"]))

        con.executemany(
            "INSERT INTO sense (sense_id, headword, definition, synonyms, source)"
            " VALUES (?,?,?,?,?)", sense_rows)
        con.executemany(
            "INSERT INTO word_char (ch, headword) VALUES (?,?)", char_rows)

        con.executemany(
            "INSERT INTO meta (key, value) VALUES (?,?)",
            [
                ("schema_version", str(config.SCHEMA_VERSION)),
                ("db_version", str(config.DB_VERSION)),
                ("built_at", datetime.now(timezone.utc).isoformat()),
                ("word_count", str(len(rows))),
                ("source_versions", json.dumps(_source_versions(),
                                               ensure_ascii=False)),
                ("license_notice", _license_notice()),
            ],
        )
        con.commit()
        con.execute("VACUUM")
        con.execute("ANALYZE")
        con.commit()
    finally:
        con.close()

    size_mb = dst.stat().st_size / 1024 / 1024
    print(f"    build_sqlite: {len(rows):,} words, "
          f"{len(sense_rows):,} senses, {size_mb:.1f} MB")
    if size_mb > 10:
        print(f"      ⚠ 용량 목표(10MB) 초과. "
              f"config.DEFINITION_MAX_CHARS({config.DEFINITION_MAX_CHARS}) 조정 검토")
    return len(rows)

def _word_row(r: dict):
    s = r["syllables"] + [None] * (5 - len(r["syllables"]))
    return (r["headword"], r["len"], s[0], s[1], s[2], s[3], s[4],
            r["tier"], r["pos"], r.get("freq_rank"), r["source"])
```

### `c3..c5` 가 NULL인 이유

2음절 단어는 `c3` 이하가 없다. `c1`, `c2` 만 `NOT NULL` (최소 길이 2).
`findByPattern`(03-03)은 `len = ?` 을 항상 조건에 넣으므로 NULL 비교를 할 일이 없다.

### `VACUUM` + `ANALYZE`

`VACUUM` 은 삭제 흔적을 정리해 파일을 줄인다. `ANALYZE` 는 인덱스 통계를 만들어
기기에서 쿼리 플래너가 올바른 인덱스를 고르게 한다 (03-03의 `EXPLAIN QUERY PLAN` 확인에 영향).

### 재현성

같은 입력 → 같은 파일이 나와야 05-01의 sha256이 안정적이다. 방해 요소:

1. `built_at` — **매번 달라진다.** 피할 수 없다. 대신 05-01은 **파일 sha256을 그때 계산**하므로
   문제되지 않는다. 다만 "입력이 같은데 파일이 다르다" 를 디버깅할 때 헷갈리니 기억해 둔다.
2. 삽입 순서 — `sort(key=headword)` 로 고정.
3. SQLite 내부 rowid — 삽입 순서가 같으면 같다.

**`app/assets/words.sqlite` 를 커밋할지 결정한다.** 10MB 바이너리다.

- 커밋 O: 클론만 하면 앱이 빌드된다. git 저장소가 갱신마다 10MB씩 커진다.
- 커밋 X: 빌드 전에 항상 ETL을 돌려야 한다. 원본 자료가 없으면 아무도 빌드 못 한다.

**권고: 커밋한다.** 원본 자료는 재배포 불가지만 파생 DB는 CC BY-SA로 배포 가능하고,
6개월에 한 번 갱신이라 저장소 증가가 느리다. 결정을 `docs/DESIGN.md` 5절에 기록한다.

## 테스트

`tools/tests/test_build_sqlite.py`

| 테스트 | 기대 |
|---|---|
| 테이블 존재 | word, sense, word_char, word_stat, meta |
| 인덱스 존재 | idx_word_c1..c5, idx_sense_headword |
| word 행 수 | `scored.jsonl` 행 수와 일치 |
| `c1..c5` 매핑 | 3음절 단어의 c4, c5가 NULL |
| `word_stat` 빈 테이블 | `SELECT COUNT(*) == 0` |
| `meta` 필수 키 | 6개 키 전부 존재 |
| 뜻풀이 길이 컷 | 모든 `definition` 길이 <= `DEFINITION_MAX_CHARS` |
| 유의어 직렬화 | 쉼표 구분, 없으면 NULL |
| `word_char` 역색인 | 단어의 각 고유 음절마다 1행 |
| FK 무결성 | 모든 `sense.headword` 가 `word` 에 존재 |
| 재실행 | 기존 파일 삭제 후 재생성, 행 수 동일 |
| **패턴 질의 인덱스 사용** | `EXPLAIN QUERY PLAN` 에 `idx_word_c2` 등장 |

마지막 테스트가 3단계 성능의 선행 검증이다:

```python
def test_pattern_query_uses_index(db):
    plan = db.execute(
        "EXPLAIN QUERY PLAN "
        "SELECT headword FROM word WHERE len=? AND tier IN (1,2) AND c2=?",
        (3, "가")).fetchall()
    text = " ".join(str(r) for r in plan)
    assert "idx_word_c2" in text, f"인덱스 미사용: {text}"
```

**이 테스트가 실패하면 인덱스 컬럼 순서를 바꿔야 한다** (02-tools-etl / 03-data-layer C절).
`tier IN (...)` 은 범위 조건이라 `(len, tier, cN)` 순서에서 `cN` 을 못 쓸 수 있다.
그 경우 `(len, cN, tier)` 로 바꾸고 schema.sql을 수정한 뒤 재빌드한다.

## 막히면

- **용량이 10MB 초과** → 순서대로: (1) `DEFINITION_MAX_CHARS` 80 → 60, (2) `word_char` 테이블 제거 검토 (03-03이 `cN` 인덱스로 충분하면 안 쓸 수도 있다 — 03-03에서 판단), (3) `freq_rank` 제거. 결정을 config 주석과 README에 기록.
- **`EXPLAIN QUERY PLAN` 에 인덱스가 안 나옴** → 위 설명대로 컬럼 순서 변경. `ANALYZE` 를 돌렸는지도 확인. 행이 몇십 개뿐인 fixture에서는 플래너가 full scan을 고르는 게 정상이므로, **이 테스트는 실데이터나 수천 행 fixture로 돌린다.**
- **FK 위반** → `sense.headword` 가 `word` 에 없다. 02-07 merge에서 senses를 자를 때 표제어가 사라졌을 수 있다. SQLite는 기본적으로 FK를 강제하지 않으므로 테스트로 직접 확인해야 한다.
- **`VACUUM` 이 느림** → 10MB면 1초 안이다. 느리면 파일이 예상보다 크다는 신호.
