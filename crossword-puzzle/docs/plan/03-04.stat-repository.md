# 03-04. 통계 저장소 (stat_repository)

담당: **AGENT**
선행: 03-03 · 다음: 03-05

## 목표

제출 결과를 `word_stat` 에 기록한다. 규칙은 단순하지만 **"첫 제출만 반영"** 판정이 까다롭다.

## 규칙

| 항목 | 값 | 근거 |
|---|---|---|
| 점수 산식 | `score = correct - wrong * 2` | REVIEW 5절 (5) |
| 코어 선택 | 점수 **낮은 순**, 동점 랜덤 | DESIGN 3.2절 |
| 반영 시점 | **첫 제출만.** 재제출은 결과만 보여주고 통계 미반영 | DESIGN 5절 |
| 빈칸 | 오답으로 집계 | DESIGN 5절 |
| `last_seen` | 제출 시각 (epoch millis) | 스키마 |

## "첫 제출" 판정

> 퍼즐 단위로 "첫 제출 여부"를 로컬에 기억(간단히 `puzzle_log` 테이블 또는 SharedPreferences)

**`puzzle_log` 테이블을 쓴다.** SharedPreferences보다 나은 이유:

- DB 하나로 끝난다. 갱신(05-03) 시 `word_stat` 과 같이 보존하면 된다.
- 퍼즐 식별자가 `(levelId, seed)` 라 구조적이다.

`tools/schema.sql` 에 테이블을 추가한다 → **02-09 재빌드 필요**:

```sql
CREATE TABLE puzzle_log (
  level_id    INTEGER NOT NULL,
  seed        INTEGER NOT NULL,
  first_score INTEGER NOT NULL,
  submitted_at INTEGER NOT NULL,
  PRIMARY KEY (level_id, seed)
);
```

`schema.sql` 을 고치면 03-01 drift 테이블과 05-03 보존 목록도 같이 고친다 (PLAN.md 3절 계약).

**대안** (재빌드가 싫으면): 앱이 첫 실행 시 `CREATE TABLE IF NOT EXISTS puzzle_log` 를 실행한다.
시드 DB는 안 바뀌고 앱이 테이블을 만든다. 05-03 보존 목록에는 여전히 추가해야 한다.
**둘 중 하나를 고르고 이 문서에 기록한다.**

### 결정: `schema.sql` 방식을 택했다

이 문서가 스스로 든 이유("DB 하나로 끝난다", "퍼즐 식별자가 구조적") 그대로다. 추가로:

- 3단계 시점에는 아직 릴리스된 앱이 없다 — 즉 "구버전 앱이 이미 깐 DB"가 존재하지 않으므로
  재빌드 비용이 곧 배포 비용이 되는 5단계(갱신) 이후와 달리 지금은 재빌드가 공짜에 가깝다.
- "앱이 `CREATE TABLE IF NOT EXISTS`로 만든다" 대안은 `03-01`이 이미 확정한 원칙
  ("시드 DB가 완성된 스키마로 온다, drift는 마이그레이션을 쓰지 않는다")을 깨고 부트스트랩
  경로에 조건부 DDL을 새로 만들어야 해서, 더 단순한 쪽을 두고 복잡한 쪽을 고를 이유가 없다.

그래서 `tools/schema.sql` 에 `puzzle_log` 를 추가하고, `python -m tools build --fixtures` 로
재빌드해 `app/assets/words.sqlite` 를 갱신했다(00-01 실데이터가 아직 없어 `--fixtures`).
`app/lib/data/db/app_database.dart`(03-01)에 `PuzzleLogs` 테이블 클래스를 추가하고
`build_runner`로 `app_database.g.dart`를 재생성했다. `docs/plan/05-03.db-swapper.md`의
보존 목록은 이미 `puzzle_log`를 넣어 두고 있어 추가 수정이 필요 없었다.

## 산출물

```
app/lib/data/
└─ stat_repository.dart
```

```dart
import 'package:drift/drift.dart';
import '../domain/model/submit_result.dart';
import 'db/app_database.dart';

class StatRepository {
  final AppDatabase _db;
  const StatRepository(this._db);

  /// 이 퍼즐이 이미 제출된 적 있는가.
  Future<bool> isFirstSubmit(int levelId, int seed) async {
    final r = await _db.customSelect(
      'SELECT 1 FROM puzzle_log WHERE level_id = ? AND seed = ?',
      variables: [Variable.withInt(levelId), Variable.withInt(seed)],
    ).getSingleOrNull();
    return r == null;
  }

  /// 제출 기록. 첫 제출이면 word_stat 반영, 아니면 아무것도 안 한다.
  /// 반환: 실제로 통계에 반영했는지
  Future<bool> recordSubmit({
    required int levelId,
    required int seed,
    required SubmitResult result,
  }) async {
    return _db.transaction(() async {
      if (!await isFirstSubmit(levelId, seed)) return false;

      final now = DateTime.now().millisecondsSinceEpoch;

      for (final r in result.results) {
        final hw = r.word.headword;
        final correct = r.isCorrect ? 1 : 0;
        final wrong = r.isCorrect ? 0 : 1;   // blank도 오답 (DESIGN 5절)
        await _db.customStatement(
          'INSERT INTO word_stat (headword, correct, wrong, last_seen) '
          'VALUES (?, ?, ?, ?) '
          'ON CONFLICT(headword) DO UPDATE SET '
          '  correct = correct + excluded.correct, '
          '  wrong = wrong + excluded.wrong, '
          '  last_seen = excluded.last_seen',
          [hw, correct, wrong, now],
        );
      }

      await _db.customStatement(
        'INSERT INTO puzzle_log (level_id, seed, first_score, submitted_at) '
        'VALUES (?, ?, ?, ?)',
        [levelId, seed, result.score, now],
      );
      return true;
    });
  }

  /// 홈 화면 누적 통계 (04-06)
  Future<({int correct, int wrong, int words})> summary() async { ... }

  /// 레벨 클리어 여부 (04-06 레벨 해제 규칙)
  Future<int?> bestScore(int levelId) async { ... }

  /// 디버그·테스트용
  Future<void> resetAll() async { ... }
}
```

### 트랜잭션이 필요한 이유

단어 20개 UPSERT + `puzzle_log` INSERT 가 원자적이어야 한다.
중간에 앱이 죽으면 "통계는 반영됐는데 첫 제출 기록이 없다" → 재제출로 이중 반영된다.

### `ON CONFLICT ... DO UPDATE`

SQLite 3.24+ (2018) 필요. 안드로이드 시스템 SQLite가 구버전일 수 있으나
`sqlite3_flutter_libs` 가 최신 SQLite를 번들하므로 문제없다. 웹 wasm도 최신이다.

## 03-03과의 연결

`coreCandidates`(03-03)의 `LEFT JOIN word_stat` 이 여기 쓴 값을 읽는다.
**통합 테스트로 한 바퀴를 확인한다:**

```dart
test('틀린 단어가 다음 생성에서 코어로 우선 선택된다', () async {
  // 1. 퍼즐 생성
  final p1 = await gen.generate(levels[0], 1);
  // 2. 일부러 다 틀린 답으로 제출
  final wrong = <(int, int), String>{
    for (final e in Scorer.solutionOf(p1).entries) e.key: '뷁'
  };
  await stats.recordSubmit(
    levelId: p1.levelId, seed: p1.seed,
    result: Scorer.score(p1, wrong, isFirstSubmit: true));

  // 3. 틀린 단어들의 점수가 음수가 됐는지
  final missed = p1.words.map((w) => w.headword).toSet();

  // 4. 같은 티어 코어 후보를 다시 뽑으면 앞쪽에 있어야 한다
  final cands = await repo.coreCandidates(
      tier: levels[0].coreTier, count: 5, seed: 1);
  final head = cands.take(10).map((w) => w.headword).toSet();
  expect(head.intersection(missed), isNotEmpty,
      reason: '틀린 단어가 코어 후보 앞쪽에 없음');
});
```

**이게 3단계 DoD 3번이다.** DESIGN 2절의 "틀린 그 단어가 다시 코어로 나와야 복습 효과" 가
실제로 동작하는지 증명한다.

## 막히면

- **`ON CONFLICT` 문법 오류** → SQLite 버전 문제. `sqlite3_flutter_libs` 가 pubspec에 있는지 확인. 정 안 되면 `INSERT OR IGNORE` + `UPDATE` 두 문장으로 나눈다(트랜잭션 안이라 안전).
- **복습 루프 테스트가 실패** → `coreCandidates` 의 `LIMIT count*12` 때문에 틀린 단어가 후보 범위 밖일 수 있다. 03-03의 `rowid` 해시 정렬이나 `LIMIT` 확대를 검토한다.
- **재제출 판정이 안 먹음** → `puzzle_log` PK가 `(level_id, seed)` 인지 확인. `Puzzle.seed` 는 `attemptSeed`(01-07)이므로 같은 퍼즐이면 항상 같다.
- **점수 산식을 바꾸고 싶음** → `docs/DESIGN.md` 5절, 01-02 계약 문서, 03-03의 SQL 세 곳을 같이 고친다.
