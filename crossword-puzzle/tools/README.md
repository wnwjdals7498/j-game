# tools — 오프라인 ETL (앱에 포함되지 않음)

사전 원본을 가공해 `words.sqlite` 를 만든다. 개발 PC에서만 실행한다.

## 실행

```powershell
tools\.venv\Scripts\Activate.ps1
pip install -r tools/requirements.txt
python -m tools build      # raw -> tools/build/words.sqlite
python -m tools report     # docs/reports/02-db-report.md 생성
python -m tools check      # 산출물 검증
```

Python 3.10 이상 필요. PC마다 `python`/`python3` 가 가리키는 버전이 다를 수 있으니
`tools/.venv/Scripts/python.exe --version` 으로 venv 안 버전을 확인할 것.

## 원본 자료

`tools/raw/` 에 둔다. 커밋하지 않는다(용량·라이선스).
자료 목록과 라이선스는 `docs/LICENSES.md` 참조.

### ⚠ 00-01 예상과 실제 포맷이 다르다 — 전부 XML/csv 가 아니라 JSON/xlsx/xls 다

00-01 문서와 최초(2026-09-16) 조사는 4개 자료가 전부 XML(사전 2종)·csv(빈도·어휘 2종)로
올 것이라 가정했다. **실제로 `tools/raw/` 에 도착한 파일은 그렇지 않다.**

| # | 자료 | 예상(00-01) | 실제 | 비고 |
|---|---|---|---|---|
| 1 | 한국어기초사전 | XML | **JSON** (LMF att/val 스타일) | 11개 파일, 총 ~1GB |
| 2 | 표준국어대사전 | XML | **JSON** (평평한 `channel.item[]`) | 88개 파일, 총 ~789MB |
| 3 | 현대 국어 사용 빈도 조사 2 | csv | **xlsx** | `일반어휘통계.xlsx` 하나만 쓴다 |
| 4 | 한국어 학습용 어휘 목록 | csv | **xls**(레거시 BIFF) | `xlrd` 는 `.xlsx` 를 못 읽는다 |

그래서 02-03(`parse_krdict`)·02-04(`parse_stdict`)는 `xml.etree.ElementTree` 대신
`json.load` 로, 02-05(`parse_freq`/`parse_vocab`)는 `csv.DictReader` 대신
`openpyxl`/`xlrd` 로 다시 작성됐다. **파일당 최대 ~99MB(기초사전 개별 파일 기준)라 파일
하나씩 통째로 `json.load` 하면 충분하다** — `xml.etree.iterparse`+`el.clear()` 같은
스트리밍 장치는 필요 없어졌다(02-01 지시). `tools/inspect_xml.py` 는 XML 전용 조사
도구라 이번 재조사에는 쓰지 않았다 — JSON/xlsx/xls 는 파이썬 REPL에서 직접
`json.load`/`openpyxl.load_workbook`/`xlrd.open_workbook` 으로 샘플링했다(스크립트 자체는
1회용이라 커밋하지 않았다. 아래 각 절이 그 결과다). XML 소스가 다시 생기면
`inspect_xml.py` 는 그대로 쓸 수 있어 남겨 둔다.

`tools/requirements.txt` 에 `openpyxl`(xlsx)·`xlrd`(xls) 를 추가했다.

기존(2026-09-16) **샘플 fixtures 기준** 조사 결과는 지워지지 않았다 — 이력 보존을 위해
이 절 끝에 "(과거) 00-01 승인 전 fixtures 기준" 으로 요약해 남겼다. 그 내용은
XML/csv 를 가정한 것이라 **더 이상 파서 구현의 근거가 아니다** — 지금은 아래 실제 구조가
근거다.

### 1. 한국어기초사전 (`tools/raw/전체 내려받기_한국어기초사전_json_20260819/*.json`)

| 고유 ID | `LexicalEntry.val`(entry 전체 id) + `Sense.val`(entry 안에서의 뜻풀이 순번, 전역 유일 아님). `sense_id` 는 `krdict:{entry.val}-{sense.val}` 로 합성 |

의도대로 작동). `drop_technical` 은 여전히 0(`DROP_TECHNICAL = False`, 02-04 "막히면" 그대로
유지 — 위 표처럼 sense 의 46%에 cat_info 가 붙어 있어 세게 걸면 안 된다).

`lxml` 은 **필요 없다.** JSON 이라 `iterparse`/`lxml` 자체가 무의미해졌다 — 파일당 최대
10.1MB 를 `json.load` 로 통째로 읽어도 88파일 전체가 6.7초다. 02-04 문서의 "메모리 계속
증가 시 lxml 전환" 절은 XML 시절 대비용이라 이제 해당 없음으로 남긴다.

## 정규화·필터 (02-06)

> ⚠ 아래 숫자는 새 픽스처(JSON, `krdict_sample.json`+`stdict_sample.json`) 기준이다.
> 실데이터 규모 실행 결과는 위 "실제 파일 구조 조사 결과 → 남은 확인 사항" 절의
> "실데이터 규모에서 파이프라인 전체 시험 실행" 참고(입력 508,912 → 통과 185,783).
> 이 절의 숫자·사유별 탈락 예시는 여전히 **픽스처(손수 만든 샘플)** 기준이다.

`tools/normalize.py` — `build/entries.{krdict,stdict}.jsonl` → `build/normalized.jsonl`.
규칙은 [docs/plan/02-06.normalize.md](../docs/plan/02-06.normalize.md) "규칙 (확정)" 절.

정규화는 **버리기 전에 고칠 수 있는 것만** 고친다: NFC → 앞뒤 공백 → 첨자(`가다¹`) → 동형어 번호(`가다01`).
띄어쓰기·`^`·하이픈은 **고치지 않는다** (다른 단어로 바꾸는 것이라 그냥 버린다 → F1).

### 실적

| 입력 | 읽은 행 | 통과 행 | 소요 시간 |
|---|---|---|---|
| 픽스처 `entries.krdict.jsonl`(21) + `entries.stdict.jsonl`(16) | 37 | **23** | 0.0s |
| **실데이터** `entries.krdict.jsonl`(76,833) + `entries.stdict.jsonl`(432,079) | 508,912 | **185,783** | 참고용(임시 실행, 위 "남은 확인 사항" 참조) |

명령: `tools\.venv\Scripts\python.exe -m tools build --only normalize --fixtures`

```
    normalize: 입력 37 → 통과 23
      F1 비한글/기호          4
      F2 길이                 2
      F3 품사                 8
      F4 어휘유형             0
      F5 고유명사             0
      F5 경고: 고유명사 탈락 0건. 입력에 판정 근거가 실려 있는지 확인할 것 (tools/README.md '미해결', 02-10 눈 검수)
```

실데이터 규모(508,912 → 185,783)로 이미 확인됐다(위 "남은 확인 사항"). **통과가 1만 미만이면**
필터가 과하거나 `pos` 실제 값이 `config.ALLOWED_POS` 와 다른 것이다(02-06 "막히면" —
`entries.krdict.jsonl` 의 `pos` 를 `Counter` 로 세어 확인) — 실데이터에서는 185,783개로
이 걱정은 해소됐다.

### 사유별 탈락 내역 (픽스처 37건)

| 코드 | 조건 | 픽스처 탈락 |
|---|---|---|
| F1 | 모든 글자가 한글 완성형 (U+AC00~U+D7A3) | 4 — `PC방` · `나무를 심다` · `발 없는 말이 천 리 간다` · `-님` |
| F2 | 길이 2~5음절 | 2 — `물`(1음절) · `국제연합기구`(6음절) |
| F3 | `pos` 가 `config.ALLOWED_POS`(`{"명사"}`) 에 있음 | 8 — `가다01`(뜻 2개) · `가다02` · `예쁘다` · `빨리` · `다고`(품사 없음) · `가늘다01`(형용사/보조 형용사 2개) |
| F4 | `word_type` 이 `config.EXCLUDE_WORD_TYPES` 에 없음 | **0** |
| F5 | 고유명사 제외 | **0** |

**F4 가 0인 이유** — 픽스처의 구·속담·관용구는 전부 표제어에 띄어쓰기가 있어 **F1 이 먼저 잡는다**
(F1 이 F2 보다 먼저라는 02-06 규칙에 따라 F1 이 맨 앞이다). 표준 쪽 구·속담·관용구는
02-04 파서가 이미 걸러 normalize 까지 오지도 않는다. **"문법‧표현"(`다고`)도 F4 후보였지만
품사가 "품사 없음"이라 F3 이 먼저 잡는다** — 02-01 재조사로 새로 추가된 `EXCLUDE_WORD_TYPES`
값이지만 픽스처로는 F4 경로가 실제로 안 켜진다(실데이터도 마찬가지일 가능성이 높다 —
문법 패턴은 대개 품사가 없거나 띄어쓰기가 있어 F1/F3 이 먼저 잡을 것으로 예상). F4 는
**품사가 있고 띄어쓰기 없는 구**가 실데이터에 있을 때를 위한 자리다. 회귀 케이스는
`test_filter` 의 `("사과", "명사", "속담") → "F4"`.

**F5 가 0인 이유** — 위 "미해결" 첫 항목. 고유명사 표시가 입력에 실려 오지 않는다.
그래서 `run()` 은 F5 가 0이면 **경고 한 줄을 반드시 찍는다** (조용히 넘어가지 않는다).

### 02-06 문서 내부 불일치 — F5 를 F3 보다 먼저 본다

02-06의 코드 골격은 `F1 → F2 → F3 → F4 → F5` 순인데, `config.ALLOWED_POS = {"명사"}` 라서
`pos == "고유명사"` 는 **F3 에서 먼저 잡히고 F5 는 영영 도달 불가**가 된다.
같은 문서의 필터 테스트 표는 `("서울", "고유명사", "일반어") → "F5"` 를 요구하고,
DoD 는 "표 기반 테스트 전부 통과"를 요구한다. 그래서 `normalize.check()` 는 **F5 를 F3 앞에 둔다.**

탈락 여부 자체는 어느 순서든 같다. 순서를 고친 이유는 02-06 3절이
**사유별 개수로 어느 필터를 완화할지 판단하라**고 했기 때문이다 — 고유명사가 품사 통계에 섞이면
그 판단을 할 수 없다. 사유는 `normalize.check()` 주석에도 남겼다.

## 표제어 결합 (02-07)

> ⚠ 아래 숫자는 새 픽스처(JSON/xlsx/xls) 기준이다. 실데이터 규모 실행 결과는 위
> "실제 파일 구조 조사 결과 → 남은 확인 사항" 절 참고(88,957 words, 빈도 매칭 34.4%,
> 등급 매칭 3.6%). `merged.jsonl`/`words.sqlite` 는 여전히 이 픽스처로 만든 것이다.

`tools/merge.py` — `build/normalized.jsonl` (+ `build/freq.jsonl` · `build/vocab.jsonl`)

앱에 싣는 뜻풀이는 `config.SENSES_PER_WORD`(=1) 개로 자른다 (DESIGN 6절 용량).
**자르기 전에 유의어만 전부 모아** `senses[0].synonyms` 에 넣는다 — 2번 뜻풀이에만
유의어가 있는 경우가 흔하기 때문이다 (02-07).

밑돌면 `run()` 이 **경고 한 줄을 반드시 찍는다** (조용히 넘어가지 않는다).

## 난이도 점수 · 7티어 (02-08)

> ⚠ 아래 숫자는 새 픽스처(19표제어) 기준이다. 실데이터 규모(88,957 words)는 티어 비율이
> `TIER_RATIO` 와 소수점까지 일치했다(위 "남은 확인 사항" 참조) — 아래 "티어 비율" 절이
> 걱정한 대로 큰 규모에서는 정확히 맞아떨어진다.

`tools/score.py` — `build/merged.jsonl` → `build/scored.jsonl` (`score`·`tier` 두 필드 추가).
`tools/hangul.py` — 자모 분해·복잡 자모 판정. 산식·비율은
[docs/plan/02-08.score-tier.md](../docs/plan/02-08.score-tier.md) 가 정한 것이고 그대로 구현했다.

```
base   = (rank - 1) / (max_rank - 1)      빈도 없음 -> NO_FREQ_BASE (1.0)
adj    = ADJ_VOCAB[grade]                 A -0.15 / B -0.10 / C -0.05
adj   += ADJ_IN_KRDICT (-0.10)            기초사전 등재
adj   += ADJ_PER_EXTRA_SYLLABLE x (음절수 - 2)   (+0.03/음절)
adj   += ADJ_COMPLEX_JAMO (+0.05)         겹받침·이중모음 포함
score  = round(clamp(base + adj, 0, 1), 6)
```

조정 손잡이는 전부 `config.py` 에 있다. 산식을 바꿀 때는 merge 까지 다시 돌릴 필요 없이
`python -m tools build --only score` 로 재실행한다 (02-08 "막히면").

### 실적

| 입력 | 읽은 행 | 출력 | 소요 시간 |
|---|---|---|---|
| 픽스처 `merged.jsonl`(19) | 19 | **19** | 0.0s |
| **실데이터** `merged.jsonl`(88,957) | 88,957 | **88,957**(참고용 임시 실행) | — |

명령: `tools\.venv\Scripts\python.exe -m tools build --only score --fixtures`

```

      tier 2        4   21.1%
      tier 3        3   15.8%
      tier 4        3   15.8%
      tier 5        2   10.5%

      tier 7        1    5.3%
```

**실데이터 규모(88,957 words)에서는 티어 비율이 25.0/22.0/18.0/14.0/10.0/7.0/4.0% 로
`TIER_RATIO` 와 소수점까지 정확히 일치했다**(위 "남은 확인 사항" 참조) — 아래 문단이
설명하는 "표본이 작아서 안 맞는" 현상이 실제로 규모가 커지면 해소됨을 확인했다.

### 티어 비율 ±1% 는 19행에서 성립하지 않는다 (샘플 크기 한계)

DoD 의 "`TIER_RATIO` 피라미드와 일치 (±1%)" 는 위 19행 로그에서 안 맞는다
(26.3 / 21.1 / 15.8 / 15.8 / 10.5 / 5.3 / 5.3 vs 목표 25 / 22 / 18 / 14 / 10 / 7 / 4).
**한 행이 5.3%p 라서 산술적으로 ±1% 안에 들어갈 수가 없다** — 산식이나 `bounds` 의
문제가 아니다. `bounds[-1] = n` 은 들어가 있고(02-08 "막히면" 점검 항목), 1000행을
넣으면 250 / 220 / 180 / 140 / 100 / 70 / 40 으로 **정확히** 떨어진다. 실데이터
88,957행에서도 위처럼 정확히 떨어졌다 — 이 절의 경고는 **작은 표본에만** 적용된다.
그래서 비율·피라미드 DoD 는 1000행 합성 입력으로 테스트에서 강제하고
(`test_tier_ratio_matches_config` · `test_tier_distribution_is_pyramid`),
19행 픽스처 로그는 실적 기록으로만 남긴다.

## schema.sql · SQLite 빌드 (02-09)

> ⚠ 아래 숫자는 새 픽스처(19표제어) 기준이다. 실데이터 규모(88,957 words) 시험 빌드는
> 33.6MB 로 용량 목표(10MB)를 넘겼다 — 위 "남은 확인 사항" 참조. 커밋된
> `app/assets/words.sqlite` 는 여전히 이 픽스처 DB 다.

`tools/schema.sql` — word · sense · word_char · word_stat · meta 5개 테이블 +
idx_word_c1..c5 · idx_sense_headword 6개 인덱스.
[docs/plan/02-09.build-sqlite.md](../docs/plan/02-09.build-sqlite.md) 의 SQL 을 그대로 옮겼다.
**이 파일이 3단계 drift 스키마(03-01)·5단계 db-swapper(05-03)와 1:1 대응하는 단일 진실**이다
(PLAN.md 3절 계약). 여기가 바뀌면 03-01·05-03 문서도 같이 고친다.

`tools/build_sqlite.py` — `build/scored.jsonl` → `build/words.sqlite`.

### 실적

| 입력 | 단어 | 뜻풀이 | word_char | 파일 크기 | 소요 시간 |
|---|---|---|---|---|---|
| 픽스처 `scored.jsonl`(19) | 19 | 19 | 52 | **0.08 MB** | 0.0s |
| **실데이터** `scored.jsonl`(88,957) | 88,957 | 88,957 | — | **33.6 MB**(참고용 임시 빌드) | — |

명령: `tools\.venv\Scripts\python.exe -m tools build --fixtures`

용량 목표는 10MB(DESIGN 6절)다. 픽스처는 0.08MB라 목표 검증이 사실상 무의미하지만,
**실데이터 규모(88,957단어)로 시험 빌드하니 33.6MB 로 목표의 3.36배를 넘었다**(위
"남은 확인 사항" 참조). 초과 시 대응은 02-09 "막히면" 순서(`DEFINITION_MAX_CHARS`
80→60 → `word_char` 제거 검토 → `freq_rank` 제거)인데, 실제로 넘긴 지금은 그 순서를
적용할지 티어 상위 N개만 담을지를 **02-10 눈 검수에서 사람이 결정**해야 한다.

### meta 6키

| key | 이번 빌드 값 |
|---|---|
| `schema_version` | `config.SCHEMA_VERSION` (1) |
| `db_version` | `config.DB_VERSION` (1) |
| `built_at` | ISO8601 UTC. **매 실행 달라진다** |
| `word_count` | 19 |
| `source_versions` | `{"origin": "fixtures", "files": {파일명: {bytes, mtime}}}` |
| `license_notice` | `LICENSE_PENDING` 문구 (아래) |

02-09 표는 두 값의 **뜻**만 정하고 계산법은 안 정했다. 문서가 준 뜻 안에서 이렇게 구현했다.

- `source_versions` — "원본 자료 버전/날짜 JSON". 자료 자체에 버전 필드가 없으므로
  입력 디렉터리(`--fixtures` 면 `tools/fixtures/`, 아니면 `tools/raw/`)를 훑어
  파일별 바이트 수·수정일을 적는다. `origin` 키가 **이 DB가 실데이터인지 샘플인지**를 말한다.
  02-10 리포트와 눈 검수가 그걸 알아야 해서 넣었다.
- `license_notice` — "`docs/LICENSES.md` 요약 문자열". 그 파일의 `## 제목` 과 바로 뒤
  `- 라이선스:` 줄을 짝지어 ` / ` 로 이은 것이다. **지금 `docs/LICENSES.md` 는 없다**
  (00-01 은 HUMAN 문서 산출물이고 아직 작성 전이다 — 자료 자체는 이제 전부 도착했다).
  없을 때는 `build_sqlite.LICENSE_PENDING`("출처 표기 미확정 …")이 들어간다.
  `docs/LICENSES.md` 가 생기면 재빌드만 하면 실제 문구로 바뀐다.

### 재현성

`built_at` 을 빼면 같은 입력 → **같은 바이트**다. 확인 방법:
`--fixtures` 로 두 번 빌드해 각각 `meta.built_at` 을 같은 값으로 덮고 `VACUUM` 한 뒤
sha256 을 비교했더니 동일했다 (`ec0cd23c4c183603…`, 81,920 바이트).

세 가지를 고정해서 얻은 결과다.

1. 빌드마다 기존 파일을 지우고 새로 만든다 (`dst.unlink()`).
2. `rows.sort(key=headword)` 로 삽입 순서를 고정 → SQLite rowid 도 같아진다.
3. `word_char` 는 `set()` 으로 고유 음절만 뽑는데, **set 순회 순서에 기대면 안 되므로**
   `char_rows.sort()` 를 한 번 더 건다. 02-09 골격에는 없던 한 줄인데, 없으면
   같은 입력에서 파일 바이트가 흔들려 05-01 의 sha256 비교가 깨진다.

`built_at` 만은 피할 수 없다. 05-01 이 릴리스 시점에 파일 sha256 을 계산하므로 문제되지는
않지만, "입력이 같은데 파일이 다르다" 를 디버깅할 때 헷갈리니 기억해 둘 것 (02-09 "재현성").

### 패턴 질의 인덱스 — 19행에서는 검증할 수 없다

`test_pattern_query_uses_index` 는 3단계 격자 탐색 성능의 선행 검증이다.
`EXPLAIN QUERY PLAN` 에 `idx_word_c2` 가 나와야 한다. 그런데 행이 몇십 개뿐이면
플래너가 full scan 을 고르는 게 정상이라, 02-09 "막히면" 이 지시한 대로
**합성 3,000행**(중복 제거 후)으로 돌린다. 픽스처 19행 DB로 같은 질의를 하면 통과하지 않는다.

`(len, tier, cN)` 순서로 통과했다 — `tier IN (1,2)` 가 범위 조건이라 `cN` 을 못 쓸 수도
있다는 02-09 의 경고는 이번에는 현실이 되지 않았다. 실데이터에서 깨지면 그때
`(len, cN, tier)` 로 바꾸고 `schema.sql` · 03-01 을 같이 고친다.

### 골격에서 바꾼 것

- 용량 초과 경고에 `⚠` 대신 `경고:` 를 쓴다. 콘솔이 cp949 일 수 있어서다
  (02-06·02-07 에서 이미 같은 이유로 정해 둔 규칙).

- `_source_versions()` 가 `use_fixtures` 를 받는다. 파이프라인이 모듈에 넘겨주는 유일한
  인자이고, 실데이터/샘플 구분이 바로 그 값이다.

3단계 격자 생성 실패율이 급증한다 (02-10 "음절 커버리지를 재는 이유", REVIEW 4.3).
03-05 측정 결과를 이 표와 나란히 놓고 볼 것.

### 규모 검사는 픽스처 빌드에서 건너뛴다

`check` 11항목 중 **단어 수(≥ 1,000)** 와 **티어 분포(±2%p)** 두 가지는 규모에 딸린
검사다. 픽스처 19행에서는 한 행이 5.3%p 라 티어 비율이 산술적으로 ±2%p 안에 들어갈 수
없고, 단어 수는 19 라 정의상 실패한다. 산식이나 `bounds` 의 문제가 아니다
(위 02-08 절 "티어 비율 ±1% 는 19행에서 성립하지 않는다" 와 같은 사정이고, 실데이터
규모(88,957행)에서는 실제로 정확히 맞아떨어졌다 — 위 "남은 확인 사항" 참조).

그래서 02-08·02-09 가 이미 쓴 방식을 그대로 따랐다 — **합성 1,000행으로 테스트에서
강제하고**(`test_check_passes_on_normal_db`, 티어가 정확히 250/220/180/140/100/70/40
으로 떨어진다) 픽스처 빌드에서는 건너뛴다. 건너뛰는 조건은 DB 안
`meta.source_versions.origin == "fixtures"` **하나뿐**이라, `--fixtures` 없이 만든
실데이터 빌드(= CI 가 보는 DB)에서는 언제나 검사한다. 양방향 회귀가
`test_check_skips_scale_checks_on_fixture_db` / `test_check_enforces_scale_checks_on_raw_db`
두 개다. 실데이터로 정식 `report`/`check` 를 돌리는 일(용량 초과 대응 결정 포함)은
02-10 눈 검수 단계로 넘긴다 — 이번 재작업(02-01)은 파서가 실데이터를 정확히 읽는지
확인하는 것까지다.

### 골격에서 바꾼 것

- `DB`/`OUT` 을 모듈 상수 `Path` 로 두지 않았다. import 시점에 `config.BUILD` 가 얼어붙어
  `config.BUILD` 를 monkeypatch 하는 02-09 테스트 방식이 통하지 않는다. 이름만 상수로 두고
  경로는 호출 시점에 만든다.
- `render(db=None, out=None)` · `check(db=None)` 로 경로 인자를 받는다. 02-10 "테스트" 표가
  "티어 8을 심은 DB", "비한글 표제어를 심은 DB" 를 요구하므로 임의의 DB 를 검사할 수 있어야 한다.
  인자 없이 부르면 골격의 `render() -> None` / `check() -> bool` 과 같다.
- 실패 표시를 `✗` 대신 `×` 로 쓴다. `✗`(U+2717)는 cp949 콘솔에서 인코딩이 터진다
  (02-06·02-07·02-09 에서 이미 같은 이유로 정해 둔 규칙). 리포트 파일은 UTF-8 이라
